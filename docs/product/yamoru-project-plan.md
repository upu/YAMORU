- 更新日: 2026-08-25

- 仮タグライン: **暮らしの「いつだっけ？」をなくす。**
- 関連文書: [YAMORU意思決定](../decisions/index.md)

## 1. エグゼクティブサマリー

YAMORUは、家族のTodo、家電や契約の情報、定期的なメンテナンス、消耗品のストック、支払い予定、実施履歴を一か所にまとめる家庭運営アプリである。

ただし、最初からすべてを作らない。まず家族専用アプリとして、「管理対象にひも付いたTodoを完了し、最後にいつ誰が行ったかと次回期限を確認できる」ことに集中する。在庫、ファイル添付、支払い、買い替えは、家庭内で中核体験が継続利用された後に追加する。

単なるTodoアプリでも、家電台帳でも、在庫管理アプリでもない。中心に置くのは、次の3要素である。

1. **家の台帳**: 家電、住宅設備、ペット用品、契約、習い事、税金などの管理対象
2. **家族のやること**: 一回限りまたは定期的なTodo、担当、期限
3. **実施履歴**: 誰が、いつ、何を行い、何を使い、いくらかかったか

代表的な問いは「猫の浄水器のフィルターを最後に交換したのはいつで、誰が交換したか」である。YAMORUは、この問いに数秒で答えられることを目指す。

## 2. 背景と解決したい問題

家庭内には、忘れると困るが、毎日意識するほどではない情報が多数存在する。

- 空気清浄機のフィルター交換
- 浄水器カートリッジの交換
- 冷蔵庫の製氷機や洗濯槽の掃除
- 家電の説明書、型番、保証期限、メンテナンス方法
- 固定資産税の納期限
- 習い事の月謝や更新手続き
- 交換用フィルターや洗剤などのストック
- 冷蔵庫やエアコンの将来的な買い替え

現在は、家族それぞれの記憶、カレンダー、Todoアプリ、紙の説明書、写真、ECサイトの購入履歴などに分散しやすい。その結果、次の問題が起きる。

- やるべきこと自体を忘れる
- 最後に実施した日や担当者が分からない
- 正しい交換部品や作業方法を毎回調べ直す
- 外出先でストックを確認できない
- 家族内で「誰かがやったと思っていた」が発生する
- 長期的な買い替えや支出を直前まで意識できない

## 3. プロダクトビジョン

### ビジョン

家の中で維持・管理・継続する必要があることを、家族の記憶に依存させない。

### 提供価値

- 家族が「次に何をするか」を共有できる
- 「最後にいつ、誰がしたか」をすぐ確認できる
- 対象物と、説明書・手順・履歴・消耗品がつながる
- 外出先からストックや予定を確認できる
- 忘れや重複購入を減らせる
- 将来の大きな買い替えや支出を早めに把握できる

### プロダクト原則

1. **入力より確認を簡単にする**
   家族全員が毎日細かく入力する前提にしない。
2. **完了履歴を上書きしない**
   実施のたびに記録を追加し、過去を追跡可能にする。
3. **予定と実績を分ける**
   定期ルール、今回の予定、実際の完了を別の概念として扱う。
4. **正確さを強制しすぎない**
   在庫は「あり / 少ない / なし」でも運用でき、必要な品だけ個数管理する。
5. **AIを正しさの基盤にしない**
   周期計算、権限、履歴は決定的なロジックで動かす。AIは将来の入力補助に限定する。
6. **家計簿を作らない**
   支払いの期限と確認は扱うが、銀行連携や包括的な収支管理は初期スコープに含めない。
7. **まず自宅で役立つものを作る**
   一般公開を前提に機能や運用を増やさず、家族で十分な期間使ってから公開の是非を判断する。

## 4. 想定利用者

### 主な利用者

- 同居する夫婦・パートナー・家族
- 子どもやペットがいる家庭
- 定期メンテナンス対象の家電や設備が多い家庭
- 家庭内の情報を一人だけが把握している状態を解消したい人

### 将来の利用者

- 一人暮らし
- 離れて暮らす家族との限定共有
- 複数の住居、実家、別荘の管理
- 賃貸物件や小規模施設の管理

初期版は、一つの家庭を家族で共有する用途に集中する。

## 5. 中核ユースケース

### 5.1 猫の浄水器フィルター

1. 猫の浄水器を登録する。
2. 商品ページまたは説明書ページへの外部リンクを保存する。
3. 「フィルター交換」を「完了日から30日後」の定期Todoとして登録する。
4. 家族の一人がTodoを完了する。
5. 完了日時と実施者が履歴に残る。
6. 次回期限が実際の完了日から30日後に設定される。
7. 後から記録する場合は、実際に交換した過去日時を指定できる。
8. 誤って完了した場合は取り消せ、取り消し自体も履歴に残る。

この一連の流れを、最初の縦切りMVPとする。

交換フィルターの在庫連動は重要な将来機能だが、最初の縦切りには含めない。

### 5.2 製氷機の掃除

- 冷蔵庫に「製氷機の掃除」を関連付ける。
- 毎月1日など、暦に固定した周期で発生させる。
- 手順やメーカーの案内ページをTodoから開ける。
- 完了履歴を冷蔵庫の詳細画面から確認できる。

### 5.3 固定資産税

- 年度と各期の納期限、金額を登録する。
- 支払いまたは口座引き落としの確認をTodoとして表示する。
- 支払い済み、確認者、確認日時を履歴に残す。
- 納付書や案内PDFを添付する。

口座情報、カード番号、認証情報は保存しない。

### 5.4 習い事

- 習い事を契約・継続サービスとして登録する。
- 月謝、支払日、更新日、休会・退会期限などを管理する。
- 規約、年間予定、連絡先へのリンクを保存する。

### 5.5 家電の買い替え計画

- 購入日、想定寿命、買い替え目安、概算費用を登録する。
- 通常のTodoとは分けて「将来計画」として表示する。
- 買い替え目安の一定期間前になったら、検討Todoを生成する。

## 7. 概念データモデル

物理的なAssetと契約・税金などのObligationは`ManagedItem`として統合する。管理上の性質は単一の`kind`、具体的な対象種別は任意の`item_type`で区別し、横断的な文脈を複数付与するタグとは役割を分ける。詳細は[YDR-028](../decisions/ydr-028-managed-item-kind-item-type-tags.md)を参照する。実運用で異なる制約が見つかった場合に分離を再検討する。

| 概念 | 役割 |
|---|---|
| Household | データを共有する家庭 |
| Member | 家族、表示名。MVPでは家庭メンバー全員が編集可能。必要なら最終利用日時を1件だけ保持。表示名は`profiles`テーブル(利用者に1対1、家庭作成前から登録可能)に保存し、MVPの一人一家庭制約下ではアカウント単位の値と家庭内表示名を同一のものとして扱う([YDR-018](../decisions/ydr-018-account-nickname-as-member-display-name.md)) |
| ManagedItem | 家電、設備、ペット用品、契約、継続的な義務など、Todoがひも付く管理対象。単一の大分類と任意の詳しい種類を持つ |
| TaskRule | 定期Todoの定義、周期、基準日、未完了時の扱い。MVPでは既定担当者を持たない |
| TaskOccurrence | 実際に発生した一回分のTodoの現在状態。本来の予定日時、現在の期限、状態、任意の担当者を保持 |
| ActivityLog | TaskOccurrenceに対する完了、取消、スキップ、延期などの追記型履歴。実施日時と記録日時を分けて保持 |
| ExternalLink | 商品ページ、メーカー説明書、メンテナンス手順などへのリンク |

MVP後に追加を検討する概念は、Consumable、StockMovement、ShoppingItem、Attachment、ReplacementPlanである。

### 7.1 重要なモデル上の判断

- 定期ルールと個別Todoを同じ行で表現しない。
- 完了日時や実施者を「前回実施日」として上書きせず、履歴を追記する。
- 完了を取り消す場合も履歴を削除せず、取消イベントを追記する。
- TaskOccurrenceはManagedItemに関連付け可能だが、通常の家族Todoとして単独でも存在できる。
- TaskRuleは次回日を暦基準または完了日時基準で計算できる。
- 周期の基準と未完了時の扱いを別の概念として扱う。
- 未完了時の扱いには「1件を持ち越す」と「回ごとに残す」がある。MVPは「1件を持ち越す」だけを実装する。
- 「1件を持ち越す」では、TaskRuleごとに未解決のTaskOccurrenceを最大1件とし、未完了なら持ち越す。
- TaskRuleは`deadline_kind`(`strict` / `maintenance`)を持つ。税金や支払いなど厳密な期限(`strict`)は`scheduled_for`と`due_at`を同日とし、`due_at`を過ぎたら期限切れのまま表示する。掃除や消耗品交換など(`maintenance`)は`scheduled_for`を推奨期間の開始、`due_at`を推奨期間の上限とし、推奨期間前・期間内・上限超過の3状態を区別して表示する（早期交換を促さない）。詳細は[YDR-017](../decisions/ydr-017-strict-deadline-vs-maintenance-recommended-window.md)を参照。
- 固定日基準の次回予定枠は、解決したOccurrenceの`scheduled_for`より後にある最初の暦上の候補から探す。候補が実際の解決日時以前なら、解決日時より後になるまで暦上の候補を進める。完了時の解決日時は`occurred_at`、スキップ時は操作日時とする。
- 例: 7月1日予定を6月28日に前倒し完了した場合は8月1日、8月10日に遅れて完了した場合は9月1日を次回とする。8月10日の完了を10月5日に記録しても次回は9月1日で、生成直後から期限切れとして表示する。
- 完了日基準のTodoは実施日時から次回を計算する。家族共有MVP（Phase 2まで）ではスキップを提供せず、Phase 3で固定日基準のスキップだけを追加する。
- TaskOccurrenceは変更しない本来の予定日時`scheduled_for`と、延期可能な現在の期限`due_at`を分けて保持する。
- 一回限りTodoは`scheduled_for`と`due_at`を両方NULLにした予定日未定のOccurrenceを持てる。後から同じ具体日を両方へ設定でき、具体日から未定へ戻す場合も両方をNULLにする。
- 同じ予定枠の重複防止は`(task_rule_id, scheduled_for)`の一意制約で担保する。
- 「1件を持ち越す」の未解決Todo重複防止は、`status = 'pending'`の行だけを対象とする`task_rule_id`の部分一意制約で担保する。
- ActivityLogは実際の実施日時`occurred_at`と、サーバーが付与する記録日時`recorded_at`を分ける。完了日基準の次回は`occurred_at`から計算し、固定日基準では前述の暦上の候補判定に`occurred_at`を使う。
- TaskOccurrenceは現在状態、ActivityLogは追記型の操作履歴として役割を分ける。
- Todo完了、履歴追加、次回生成は一つのトランザクションとして扱う。完了処理は`pending`のOccurrenceだけを条件付きで更新し、その更新に成功した要求だけが完了履歴と次回Occurrenceを作る。
- 同じ完了要求が再送されても二重記録されないよう、冪等性を持たせる。
- 完了取消は、取消履歴の追記、自動生成された未変更の次回Occurrenceの削除、元Occurrenceの`pending`への復帰を一つのトランザクションで行う。
- 取消対象の完了後に生成された次回Occurrenceへ、延期、担当変更、完了などの利用者操作が一つでも記録されている場合は取消を拒否し、手動訂正を案内する。未変更の派生Occurrenceだけを削除するため、追記型履歴の原則とは矛盾しない。
- TaskRuleには既定担当者を持たせない。TaskOccurrenceの担当者は既定で未設定とし、「誰でも可」として扱う。
- 日時はUTCで保存し、家庭のタイムゾーンで表示・周期計算する。
- 金額は浮動小数点で保存しない。
- アプリの開封イベント履歴は蓄積しない。必要なら運用確認用の`last_seen_at`を1件だけ上書きし、家族の評価やランキングには使用しない。

## 8. MVPの範囲

本プロジェクトでいう家族共有MVPはPhase 1とPhase 2で構成する。Phase 0は実装前の準備として扱う。

### 必須

- メールまたは外部IDによるログイン
- 家庭の作成と家族招待
- 家庭メンバー全員が編集できる単純な権限モデル
- 名前、種類、外部リンクだけを持つ最小限のManagedItem
- 家族Todoの作成、任意の担当、完了
- 一回限り、固定周期、完了日基準周期
- 一回限りTodoの予定日未定、後からの予定日設定・未定化
- TaskRuleごとに未解決Todoを最大1件とする持ち越し方式
- 本来の予定日時と現在の期限の分離
- 完了日時を過去に指定できるバックデート完了
- 実施日時と記録日時を分けた追記型履歴
- 直近の完了だけを対象とし、生成後の次回Todoが未変更の場合に限る完了取消
- 延期
- ManagedItem詳細上部の「最後にいつ、誰が」表示
- 今日、期限切れ、近日の一覧
- スマートフォン対応PWA
- 家族単位のアクセス制御
- 同じ操作の再送に対する冪等性
- ホーム画面に、期限切れ、今日、近日、最近の実施を常時表示
- 未完了Todoをすべて確認し、担当変更・完了・予定日設定を行えるTodo一覧画面
- Todoの詳細画面と、繰り返しなしTodoの名前・関連ManagedItem・担当・予定日の編集

### MVP後に追加を検討するもの

- 消耗品と在庫移動履歴
- 買い物候補
- PDF・写真のアップロード
- 支払い期限、金額、確認者
- 月謝や税金向けの、各予定回を個別に残す方式
- スキップ
- 買い替え目安と概算費用
- 検索、テンプレート、複数住宅

### 初期スコープ外

- Realtime購読
- Owner / Memberなどの細かな権限区別
- 銀行、カード、家計簿との連携
- IoT機器や重量センサーとの連携
- ECサイトからの自動購入
- 高度な会計、予算管理
- AIによる自動判断や自動スケジュール確定
- OCRによる説明書・型番の自動登録
- ネイティブアプリ、ウィジェット、Apple Watch
- 業者や家庭外ユーザーとの共有
- 複数住宅を前面に出したUI
- 一般公開を前提とした課金、サポート、規約、ストア対応

## 9. UX方針

### 日常操作

- ホームから一操作で完了できる。
- ホームはいま対応することに絞り、それ以外の未完了Todoはホームからのリンクで開くTodo一覧で確認する。下部ナビゲーションは「ホーム」「台帳」の2項目を保つ。
- 完了時に、担当者、使用数、費用、写真、メモを必要な場合だけ追加できる。
- 何も追加入力しなくても完了できる。
- 「最後にいつ、誰が」を詳細画面の上部に常に表示する。

### 登録操作

- 最初から全項目を求めない。
- Todo名だけで一回限りTodoを作成でき、予定日が決まっている場合だけ具体日を入力する。
- 繰り返しなしTodoは、登録後にTodo詳細から名前・関連ManagedItem・担当・予定日を編集できる。予定日は具体日と未定を往復できる。
- ManagedItemは単一の大分類と、プリセットまたは自由入力による任意の詳しい種類を登録・編集できる。
- ManagedItemの名前は家庭内での呼び名とし、メーカー名・商品名・型番などは一つの任意の商品情報として別に残す。型番だけを独立した必須項目にしない。
- 購入時期は分かる精度（年、年と月、年月日）だけを残せる。分からない月日を推測入力させない。
- タグ、詳しい属性、説明書、消耗品などは後から段階的に追加できる。
- サンプルテンプレートを用意するが、自動で大量登録しない。

### 家族利用

- 誰かを責める家事分担アプリにしない。
- 実施量のランキングやポイントは初期版に含めない。
- 担当者未定や「誰でも可」を許容する。
- 操作履歴は監視ではなく、引き継ぎと確認のために見せる。

- Auth.js Credentials + JWTセッション
- household_idを必須にしたデータアクセス層とアプリ層認可

Realtime、Storage、CronはMVPでは使用しない。家族の更新は、画面表示時・フォーカス復帰時・明示的な再読み込みで取得する。ファイル添付を追加する段階でStorageを導入する。

### 配信・運用

- Cloudflare Workersを配信先とする
- D1のマイグレーションをリポジトリ管理する
- 開発、ステージング、本番を分離する
- エラー監視と構造化ログを導入する
- 定期的なエクスポートまたはバックアップ方針を設ける

### テスト

- 単体テスト: Vitest
- UIテスト: Testing Library
- E2E: Playwright
- データベース権限: 実D1上の家庭A/B・非メンバー・未認証・IDOR境界テスト
- 周期計算: 前倒し・遅延・バックデート、タイムゾーン、月末、うるう年、延期、スキップを重点的に検証

### ネイティブ化の判断条件

以下がPWAで重大な制約になり、家庭内運用が成立しない場合、Expo / React Nativeを検討する。

- ホーム画面ウィジェット
- バーコードやQRコードの継続的な利用
- オフライン利用
- OS共有機能との深い統合

## 11. セキュリティ・プライバシー

YAMORUには家族構成、所有物、契約、税金、写真、説明書など、生活に密接なデータが入る。

- すべての家庭データにhousehold_idを持たせる。
- 家庭データへ触れるすべてのデータアクセス関数でmembershipを検証し、更新・削除SQLにもhousehold_id条件を含める。
- 将来Storageを導入する場合も、家庭メンバー以外からアクセスできないよう制御する。
- 招待リンクは期限付き・一回限りとする。
- Cloudflare APIトークンや`AUTH_SECRET`などの管理者権限の認証情報をクライアントへ公開しない。
- 口座番号、カード番号、パスワードなどの秘密情報を保存しない。
- 削除、退会、家庭からの離脱、データエクスポート方針を初期段階で決める。
- 家族から外れたユーザーのアクセスを即時に失効させる。
- 履歴修正は、過去を黙って書き換えるのではなく訂正記録を残す。

- `occurred_at`と`recorded_at`の分離
- 次回Todo生成
- 予定枠と未解決Todoの二種類の一意制約
- 同時完了時に一件だけ成功させる条件付き更新とトランザクション
- ManagedItem詳細の「最後にいつ、誰が」表示

完了条件:

### Phase 2: 家族共有MVP

目的: 実際の家庭で二人以上が利用できる。

- HouseholdとMember

完了条件:

### Phase 3: 日常利用の完成

目的: 毎日開いても負担にならない状態にする。

- スキップ、担当変更
- 件数と期限が一目で分かる要対応サマリー
- ホーム画面の絞り込みと情報優先順位の改善
- モバイル操作改善
- 月1回5分程度、期限超過、予定との差、記録の遅れ、具体的な困りごとを家族で確認する軽量レビュー

完了条件:

- 家族が説明なしでTodoを確認・完了できる。
- 家族が「最後にいつ、誰が」を10秒以内に確認できる。

## 13. 最初の受け入れテスト

「猫の浄水器フィルター」を使い、次を確認する。

1. 浄水器を登録できる。
2. 商品ページまたは説明書ページへの外部リンクを追加できる。
3. フィルター交換を完了日基準30日で設定できる。
4. 家族Aがフィルター交換を完了できる。
5. 詳細画面に、家族Aと完了日時が表示される。
6. 次回期限が実際の完了日時から30日後になる。
7. 家族Bがアプリを開くと変更が反映される。
8. 家族Bが「最後にいつ、誰が交換したか」を10秒以内に確認できる。
9. 家族Aが「3日前に交換した」として完了を記録でき、次回期限がその日から30日後になる。
10. 誤って完了した操作を取り消せ、取り消したこと自体が履歴に残る。
11. 完了後に自動生成された次回Todoが未変更なら取り消せ、次回Todoに操作済みなら安全に拒否される。
12. 同じ完了操作が再送された場合や家族二人が同時に完了した場合も、完了履歴や次回Todoが二重に作られない。
13. 固定日基準の7月1日予定を6月28日に完了すると次回は8月1日になり、8月10日に完了すると次回は9月1日になる。
14. 8月10日に実施した完了を10月5日に記録すると、9月1日の次回Todoが期限切れとして生成される。
15. Phase 2で延期した場合も`scheduled_for`は変わらず、`due_at`だけが変わる。

## 14. 主なリスクと対策

| リスク | 対策 |
|---|---|
| 家庭運営OSへ際限なく膨らむ | 猫の浄水器ユースケースを最初の品質基準にする |
| 入力が面倒で家族が使わない | 最小入力、一操作完了、任意項目、テンプレート |
| 定期処理が複雑化する | 固定日基準と完了日基準から始め、ルールと実体を分離する |
| アプリを開かず期限を忘れる | 期限超過と家族の具体的な困りごとを月次で確認し、通知で防げる実害が繰り返された場合のみ再検討する |
| Todo完了と次回Todoが不整合になる | トランザクション、条件付き更新、二種類の一意制約、冪等性キーを使う |
| 家庭間でデータが漏れる | RLSテストを必須ゲートにする |
| 履歴が監視や責任追及に見える | ランキングを避け、引き継ぎのための表示にする |
| 支払い機能が家計簿へ膨らむ | 期限、金額、確認、資料に限定する |
| 実施したが記録し忘れる | バックデート完了を必須にし、現実の履歴へ修正できるようにする |
| 公開前提の作業で完成が遠のく | まず家族専用とし、一般公開の判断をPhase 7まで凍結する |

## 15. 成功指標

初期段階では利用者数ではなく、家庭内での有用性を測る。

- 家族の二人以上が自発的に利用する
- 開発者以外の家族による完了記録が、家庭内運用中に継続して発生する
- 「最後にいつ、誰が」を10秒以内に確認できる
- 記録し忘れてもバックデートにより現実と整合させられる
- 数週間以上の家庭内利用で、開発者以外の家族もホーム画面を自発的に確認する
- ホーム画面だけで期限切れ、今日、近日の状況を把握できる
- 交換忘れを実際に一度以上防げる
- 1件の完了操作に必要な入力が過剰でない

月次の軽量レビューでは、単純な利用回数ではなく、次を分けて確認する。

- 実際の実施日時と現在期限の差: `occurred_at - due_at`
- 実際の実施日時と本来の予定の差: `occurred_at - scheduled_for`
- アプリへ記録するまでの遅れ: `recorded_at - occurred_at`
- 通知や機能追加で防げそうな、実際に起きた失敗や困りごと

## 16. 現時点の決定事項

この章は意思決定の要約である。現在有効な判断とその理由は、[意思決定の索引](../decisions/index.md)からたどれるYDRを正本とする。

- プロダクト仮称はYAMORU。
- タグライン案は「暮らしの『いつだっけ？』をなくす。」。
- ヤモリをロゴまたはマスコットのモチーフにする。
- 家族Todo、家の台帳、実施履歴を中核にする。
- まず家族専用として作り、一般公開は数か月以上使った後に判断する。
- Phase 1にも、名前・種類・外部リンクだけの最小限の台帳を残す。
- MVPでは外部リンクだけを扱い、PDFと写真は後から追加する。
- 在庫管理はMVP後に追加し、簡易状態を既定とする。
- 固定資産税や月謝は、家計簿ではなく期限付き義務として扱う。
- 長期的な買い替えは、通常Todoとは別の将来計画として扱う。
- PWAから始め、必要性が確認された場合のみネイティブ化する。
- フロントエンドはNext.jsで実装する。
- 初期版にはPush、メール、カレンダー連携などの通知機能を含めない。
- 通知相当の内容はホーム画面に常時表示し、通知は実害が確認された場合だけ再検討する。
- MVPではRealtimeと細かな権限区別を作らない。
- TaskRuleに既定担当者を持たせず、TaskOccurrenceの担当者は未設定を既定とする。
- バックデート完了と完了取消をMVPに含める。
- MVPではTaskRuleごとに未解決Todoを最大1件とする。
- 掃除やメンテナンスは未完了を1件に持ち越し、月謝や税金の各回を残す方式は支払い機能と同時に追加する。
- 「回ごとに残す」方式を後から有効にしても、有効化以前の予定回は自動生成しない。
- TaskOccurrenceは現在状態、ActivityLogは操作履歴として扱う。
- 固定日基準の次回予定枠は、元の`scheduled_for`から暦を進め、実際の解決日時以前の候補を飛ばして決める。
- 完了取消は、自動生成された次回Todoが未変更の場合だけ許可する。
- アプリ開封履歴は蓄積しない。必要なら最終利用日時だけを上書き保持する。
- AIは初期版の必須要素にしない。
- 一回限りTodoだけ予定日未定を許し、日付が決まった後も具体日と未定を往復できる。
- ホームは「いま対応すること」、Todo一覧は「未完了Todoすべて」として役割を分ける。7日より先の予定と完了日基準Todoの推奨期間前は、ホームではなくTodo一覧で確認する。
- Todoを確認・編集する正規の場所はTodo詳細とする。ホームとTodo一覧のTodo名からは同じTodo詳細へ、管理対象名からは管理対象の詳細へ移動する。
- 内容の編集は繰り返しなしTodoに限り、名前・関連ManagedItem・担当・予定日を対象とする。繰り返し方や繰り返し規則の変更は当面扱わない。
