# YAMORU レビュー依頼プロンプト集

`docs/product/yamoru-project-plan.md`と`docs/decisions/index.md`(および索引からたどれる各YDR)をClaude Code、Codex、その他のAIや人間のレビュアーに渡す際に使用する。

意思決定ログの`Accepted`項目にも反対意見を出してよいが、その場合は、既存の理由を読んだうえで、新しい証拠・見落とし・具体的な不利益を示すことを求める。

## 1. 総合レビュー

```text
docs/product/yamoru-project-plan.mdとdocs/decisions/index.md(索引からたどれる各YDR)を読んで、このプロダクト構想と実装計画をレビューしてください。

現時点では実装を変更せず、レビューだけを行ってください。

特に以下を確認してください。

1. 解決する問題と対象利用者が明確か
2. 機能の集合ではなく、一貫したプロダクトになっているか
3. MVPが広すぎないか。残すものと後回しにするもの
4. 「家の台帳」「家族Todo」「実施履歴」「ストック」の関係
5. 猫の浄水器フィルターを最初の縦切りにする妥当性
6. 家族が継続利用するうえでの入力負担や心理的な問題
7. 計画内の矛盾、曖昧さ、暗黙の前提
8. 重大な見落とし

回答は次の順にしてください。

- 総評
- 良い判断
- 重大な懸念（重要度順）
- MVPから削るもの
- MVPに不足しているもの
- 未決事項への推奨回答
- 修正版のMVP定義
- 次に行うべき3つの作業

推測と事実を分け、過度に機能を追加しないでください。
意思決定ログでAcceptedになっている判断を変更すべきと考える場合は、既存の判断理由を踏まえ、変更を正当化する新しい根拠を示してください。
```

## 2. アーキテクチャレビュー

```text
docs/product/yamoru-project-plan.mdとdocs/decisions/index.md(索引からたどれる各YDR)の技術構成と概念データモデルを、シニアソフトウェアアーキテクトとしてレビューしてください。

まだコードは書かないでください。

重点項目:

- Next.js PWA + Supabaseという選択
- Household単位のマルチテナント設計
- Supabase RLSと招待受諾フロー
- TaskRule / TaskOccurrence / ActivityLogの分離
- 固定日基準と完了日基準の定期Todo
- TaskRuleごとに未解決Occurrenceを最大1件とするMVP方針
- 将来の「回ごとに残す」方式を妨げない設計
- 「回ごとに残す」方式を後から有効にしても過去分を自動生成しない方針
- scheduled_for / due_at と occurred_at / recorded_at の分離
- 固定日基準で、元のscheduled_forから次の暦上の候補を探し、実際の解決日時以前の候補を飛ばす計算
- Todo完了、履歴追加、次回生成のトランザクション
- `(task_rule_id, scheduled_for)`の一意制約
- pending行だけを対象とするtask_rule_idの部分一意制約
- pending行の条件付き更新による、家族二人の同時完了の競合防止
- 二重送信に対する冪等性
- TaskOccurrenceを現在状態、ActivityLogを追記型履歴とする役割分担
- 完了取消時に、未変更の次回Occurrenceだけを削除し、操作済みなら取消を拒否する方針
- CronとRealtimeを使わないMVP構成
- 通知なしでも期限切れ・今日・近日を正しく表示できるホーム画面とOccurrence生成
- UTC保存と家庭タイムゾーンでの計算
- PDFや写真などの家庭内機密データ
- 将来のネイティブ化を妨げる設計がないか

回答には以下を含めてください。

1. 重大度付きの問題一覧
2. 推奨するデータモデルの修正
3. 境界を明確にすべきドメイン操作
4. 最初に技術検証すべきリスク
5. セキュリティテスト項目
6. MVPに不要な技術的複雑性
7. 推奨するADRの一覧

特に次の具体例について、期待結果とデータベース上の状態遷移を確認してください。

- 7月1日予定を6月28日に前倒し完了すると次回は8月1日
- 7月1日予定を8月10日に遅れて完了すると次回は9月1日
- 8月10日の完了を10月5日に記録すると、9月1日の次回Todoが期限切れで生成される
- 家族二人が同じTodoを同時に完了しても、完了履歴と次回Todoは一件ずつ
- 次回Todoが未変更なら完了取消でき、延期や担当変更などの操作済みなら安全に拒否される

一般論や新機能の追加ではなく、YAMORUの具体的なユースケースとPhase 0着手前に修正すべき矛盾へ絞ってください。
```

## 3. UX・家族利用レビュー

```text
docs/product/yamoru-project-plan.mdとdocs/decisions/index.md(索引からたどれる各YDR)を、家庭向けアプリのプロダクトデザイナーとしてレビューしてください。

YAMORUは家事の成績や家族の監視を目的とせず、家庭内の記憶と引き継ぎを助けるアプリです。

次の観点を重点的に確認してください。

- 家族が毎日細かく入力しなくても成立するか
- Todo完了操作が十分に軽いか
- 「誰がやったか」が責任追及に見えないか
- 「最後にいつ、誰が」がすぐ分かるか
- 普通のTodoと定期メンテナンスが自然に共存するか
- 家電、契約、税金、習い事を一つの台帳に見せて混乱しないか
- 在庫の「あり / 少ない / なし」と個数管理の共存
- 初回登録で挫折しないか
- 通知なしでも、期限切れや近日のTodoに気づける情報優先順位になっているか
- 高齢者や子どもを将来含められるか

以下を提案してください。

1. 主要ナビゲーション
2. ホーム画面の情報優先順位
3. 猫の浄水器詳細画面の構成
4. Todo完了フロー
5. 初回オンボーディング
6. 削るべき入力項目
7. ユーザビリティテストのシナリオ

画面数や機能を増やしすぎず、MVPとして提案してください。
```

## 4. プラン改訂依頼

複数レビューを受けた後に使用する。

```text
docs/product/yamoru-project-plan.md、docs/decisions/index.md(索引からたどれる各YDR)、以下に貼り付ける複数のレビュー結果を比較してください。

目的は、レビューを無条件に全部採用することではなく、YAMORUの目的に照らして妥当な指摘だけを反映した改訂案を作ることです。

各指摘について以下を判断してください。

- 採用
- 一部採用
- 見送り
- 追加調査

判断理由を短く示してください。レビュー同士が矛盾する場合は、その対立点と推奨判断を示してください。

その後、次を出力してください。

1. 意思決定一覧
2. 改訂後のMVP
3. 改訂後のロードマップ
4. 改訂後の未決事項
5. docs/product/yamoru-project-plan.mdに対する具体的な変更案
6. docs/decisions/配下に、新規YDRの追加・既存YDRのSupersededとして記録すべき内容

スコープ追加よりも、明確化と単純化を優先してください。

--- レビュー結果 ---
ここにレビューを貼り付ける
```
