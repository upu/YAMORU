# YDR-037: 固定間隔の繰り返しを起点日と間隔日数が決める候補列として定義する

- 状態: Accepted
- 決定日: 2026-08-31

## 背景

現在の繰り返しは、完了日基準(`recurrence_basis = 'completion'`、完了日から推奨期間のオフセットを足す)と、定例日基準(`recurrence_basis = 'calendar'`、曜日・日付に固定する。[YDR-021](ydr-021-recurring-calendar-rules.md))の二つである。

一方、実利用には「起点日から10日ごと」「2週間ごと(隔週)」のように、暦の曜日・日付には固定されないが、完了が遅れても周期そのものはずらさない繰り返しがある([Issue #97](https://github.com/upu/YAMORU/issues/97))。これは既存の完了日基準の「N日後」と入力の見た目が似ているが、遅れて完了したときの次回予定日が異なる。

意味の違いを決めないまま実装すると、利用者が選んだ意図と保存された規則がずれ、[YDR-013](ydr-013-fixed-date-next-occurrence-calculation.md)の次回計算や[YDR-014](ydr-014-unique-constraints-and-conditional-update.md)の重複防止とも整合しなくなる。この決定は、実装(UI・DBスキーマ)に先立って、起点、候補生成、遅延時の扱い、日と週の意味、入力制約、保存形式の候補を定める。

## 決定

### 1. 完了日基準との意味の違い

- 完了日基準は、次回の`scheduled_for`を実際の完了日から決める(`occurred_at + recommended_start_offset`日)。周期は完了のたびに実際の完了日へ吸着し、遅れた分だけ以降の予定も後ろへずれる。
- 固定間隔は、候補列を起点日と間隔だけで決める。完了日は「候補列のどこまで進むか」を決めるだけで、候補列そのものを動かさない。遅れて完了しても、以降の予定日は最初に決めた周期の上に載り続ける。
- 例: 起点8月1日・10日ごとの候補列は 8/1, 8/11, 8/21, 8/31, 9/10 …。8月11日予定を8月16日に完了した場合、固定間隔の次回は8月21日、完了日基準(10日後)の次回は8月26日になる。

### 2. 起点と候補列

- TaskRuleは起点日(anchor)を1件持つ。起点日はAsia/Tokyoの暦日(`YYYY-MM-DD`)であり、瞬間ではない。
- 候補列は、起点日を`A`、間隔日数を`D`として、暦日`S_k = A + k × D`(`k = 0, 1, 2, …`)とする。別のアンカー日を持たず、初回予定日をそのまま起点とする。
- 候補の`scheduled_for`は、その暦日のAsia/Tokyo 00:00を表す瞬間とする([YDR-021](ydr-021-recurring-calendar-rules.md)の1と同じ変換)。UTCの日付境界では判定しない。
- 起点日は登録時に確定し、完了・スキップ・完了取消で書き換えない。「遅れて完了しても周期が完了日に引きずられない」ことは、起点日を書き換えないことによって担保する。
- 登録時は利用者が初回予定日を指定し、その値を起点日とする。指定がない場合は登録日(Asia/Tokyoの暦日)を起点日とする。
- 起点日は登録日より前でもよい(すでに家庭で回っている周期をそのまま登録できる)。その場合の初回Occurrenceの`scheduled_for`は、登録日の暦日を含め、それ以降で最初の候補とする(YDR-021の6と同じ規則)。起点日から登録日までの間に位置する候補は、[YDR-016](ydr-016-no-backfill-on-per-occurrence-mode.md)に従いさかのぼって作成しない。
- 候補の探索・生成は常にサーバー側でTaskRuleの規則から計算する。クライアントから`scheduled_for`や起点日以外の計算結果を受け取って採用しない(YDR-021の6と同じ)。

### 3. N日とN週の意味

- N日は、Asia/Tokyoの暦日をN日加算する意味とする(既存の完了日基準オフセットが使う`addTokyoDays`と同じ暦日加算)。時刻の差ではない。
- N週は、常に7×N日の間隔とする。Asia/TokyoはDSTを持たないため、7×N日の暦日加算は必ず同じ曜日に着地する。したがって「曜日を保つ週単位の規則」を日の規則とは別に定義せず、週は日の別表記として扱う。
- 内部の候補計算は、常に間隔日数`D = interval_count × (unit が week なら 7、day なら 1)`へ正規化してから行う。
- 単位と回数を分けて保存するのは、計算のためではなく利用者の意図(「隔週」なのか「14日ごと」なのか)を保存・表示に残すためである([YDR-032](ydr-032-monthly-day-month-end.md)で「毎月末」と「毎月31日」を区別したのと同じ理由)。
- Nか月ごと・N年ごとは、暦月・暦年の長さが一定でなく候補列の定義自体が別問題になるため、この決定では扱わない。

### 4. 次回候補の決め方(YDR-013との整合)

- 次回候補は[YDR-013](ydr-013-fixed-date-next-occurrence-calculation.md)をそのまま適用して決める。すなわち、直前に解決したOccurrenceの`scheduled_for`と、実際の解決日時の**両方より後**にある最初の候補を次回とする。
- 実際の解決日時は、完了時は`occurred_at`、スキップ時は操作日時とする。`recorded_at`は次回候補の計算に使わない。
- 候補列は等差数列であるため、候補を1件ずつ進める反復探索は不要で、次の閉じた式で求められる。直前のOccurrenceの候補添字を`j`(`S_j = A + j × D`)、解決日時のAsia/Tokyo暦日を`d`とすると、次回の添字は
  `k = max(j + 1, max(0, floor((d − A) / D) + 1))`
  であり、`floor`は暦日差の整数除算とする。`S_k`は`S_j`より後、かつ`d`より後の最初の候補になる。
- 前倒し完了(解決日時が直前の`scheduled_for`より前)では、`k = j + 1`となり、周期は1回分だけ進む。
- 遅延完了で飛ばした候補は、YDR-016に従いさかのぼって作成しない。次回Occurrenceは常に1件だけ作る。
- 過去日時での完了(バックデート)は`occurred_at`で判定するため、記録した時点ではすでに期限を過ぎた次回が生成されることがある。これはYDR-013が固定日基準について示した挙動と同じであり、固定間隔でも例外を作らない。

例(起点8月1日・10日ごと。候補列は 8/1, 8/11, 8/21, 8/31, 9/10 …):

| 直前の予定 | 実際の解決 | 次回 | 理由 |
|---|---|---|---|
| 8月11日 | 8月8日に完了(前倒し) | 8月21日 | 8月11日より後の最初の候補 |
| 8月11日 | 8月16日に完了(遅延) | 8月21日 | 完了日基準の10日後(8月26日)とは異なる |
| 8月11日 | 8月25日に完了(遅延) | 8月31日 | 8月21日は飛ばし、さかのぼって作らない |
| 8月11日 | 9月5日に完了し、9月20日に記録 | 9月10日 | `recorded_at`は使わないため、生成直後から期限切れ |

隔週(2週=14日)で起点が8月3日(月曜)なら、候補列は 8/3, 8/17, 8/31 … となり、遅延完了があっても常に月曜のままになる。

### 5. 単一pending Occurrence・同時完了との整合

- 次回候補は、TaskRuleの起点日・間隔と、解決したOccurrenceの`scheduled_for`・解決日時だけから決まる決定的な関数である。同じ完了要求を家族が別端末から同時に処理しても、計算される`scheduled_for`は同一になる。
- したがって[YDR-014](ydr-014-unique-constraints-and-conditional-update.md)の二種類の一意制約(`(task_rule_id, scheduled_for)`の一意制約と、`status = 'pending'`に対する`task_rule_id`の部分一意制約)がそのまま二重生成を防ぐ。次回Occurrenceを作れるのは、`pending`への条件付き更新に成功した1件だけとする点も変更しない。
- 間隔日数は常に1以上であるため候補列は厳密に単調増加し、同じTaskRuleが同じ`scheduled_for`を二度生成しない。`(task_rule_id, scheduled_for)`の一意制約は、この決定によって新たに壊れることはない。
- 解決のたびに次回を1件だけ作り、飛ばした候補を作らない(YDR-016)ため、TaskRuleごとのpending Occurrenceは最大1件のまま維持される。完了取消は[YDR-015](ydr-015-occurrence-state-activitylog-history-safe-undo.md)の規則をそのまま適用し、この決定では変更しない。

### 6. 保存形式の候補

実装(#97の対象外)で選ぶための候補を、次のとおり記録する。

- 繰り返し方は、既存の3値に意味を重ねず、新しい`recurrence_basis = 'interval'`として表す。完了日基準の`recommended_start_offset`は「完了日からの相対日数」であり、固定間隔の「候補列の間隔」とは意味が異なるため流用しない。
- 規則は`task_rules`の3列で表す。`interval_unit`(`'day'`または`'week'`)、`interval_count`(整数)、`interval_anchor_on`(Asia/Tokyoの暦日、`YYYY-MM-DD`)。`interval_anchor_on`は暦日であり、`task_occurrences.scheduled_for`(瞬間)とは型も意味も別である。
- 期限の扱いは`calendar`と同じく`deadline_kind = 'strict'`、`recommended_start_offset = 0`、`recommended_until_offset = 0`とし、`scheduled_for`と`due_at`を同日として扱う([YDR-017](ydr-017-strict-deadline-vs-maintenance-recommended-window.md))。`schedule_kind`などの定例日指定列はすべてNULLとする。
- `task_rules`の`recurrence_basis`と方式ごとの列の組み合わせは複合CHECK制約で表現されており、SQLiteではCHECK制約の列挙をそのまま拡張できない(YDR-032の1と同じ制約)。手段は、テーブル再作成(`task_occurrences`からの複合外部キーを含めて作り直す。`0009_undated_one_time_todos.sql`に前例がある)か、列追加とTRIGGERの組み合わせのいずれかとし、実装Issueで選ぶ。
- どちらの手段を選んでも、「`recurrence_basis = 'interval'`の行だけが`interval_*`列を非NULLで持ち、他の方式の行では必ずNULLである」という越境不変条件はデータベース側で守る。アプリ層の検証だけに任せない。
- 既存行の移行は不要である。この決定は既存の`completion` / `calendar` / `once`の行の意味を変えない。

### 7. 入力制約

- `interval_count`は整数のみとし、小数・0・負値を拒否する。上限は`interval_unit = 'day'`のとき1〜3650、`interval_unit = 'week'`のとき1〜520(=3640日)とする。いずれも既存の`recommended_start_offset` / `recommended_until_offset`の上限(3650日、約10年)に合わせた値である。
- `interval_anchor_on`は実在する暦日に限り、登録日の3650日前から3650日後までの範囲とする。
- 範囲外・非整数・実在しない日付はTaskRuleの登録時に拒否し、候補計算へ渡さない(YDR-021の2と同じ方針)。
- 候補計算は4の閉じた式で行い、候補を1件ずつ進める反復探索をしない。極端に遅れた完了や長い間隔でも計算量は一定であり、上記の入力上限により暦日差も有界であるため、オーバーフローや長時間ループは起きない。

### 8. 表示名

- 繰り返し方の選択肢は「繰り返しなし」「完了した日から繰り返す」「一定の間隔で繰り返す」「曜日・日付で繰り返す」の4つとし、固定間隔を独立した選択肢として並べる。
- 既存の2つのラベル(「完了した日から繰り返す」「曜日・日付で繰り返す」)は変更しない。利用者の再学習を避けるためであり、区別は次の補足文で行う。
  - 完了した日から繰り返す: 完了した日を起点に次回を決める。遅れて完了すると、その分だけ次回も後ろへずれる。
  - 一定の間隔で繰り返す: 起点日から一定の間隔で予定する。遅れて完了しても周期はずれない。
- Todo詳細の繰り返しパターン表示(YDR-032の4で追加した行)には、「8月1日から10日ごと」「8月3日から2週間ごと」のように起点日と間隔を表示する。週指定を日数へ言い換えて表示しない。

### 9. この決定で扱わない範囲

- UI・DBスキーマ・候補計算の実装そのもの(別Issueで行う)。
- Nか月ごと・N年ごとの固定間隔。
- 毎週の複数曜日、毎月・毎年の第N曜日といった暦規則の拡張。
- 通知、祝日・営業日補正。
- 登録後に繰り返し規則(起点日・間隔・繰り返し方)を編集する導線。現在の編集対象は繰り返しなしTodoに限られており、この決定では広げない。
- 固定間隔と`deadline_kind = 'maintenance'`(推奨期間)の組み合わせ。

## 結果

- 「一定の間隔で繰り返す」と「完了した日から繰り返す」の違いが、保存形式・候補計算・表示のそれぞれで区別できる。
- 遅延完了、前倒し完了、過去日時での完了、同時完了のいずれでも、次回候補が一意に決まる。
- YDR-013の次回計算アルゴリズム、YDR-014の重複防止、YDR-016の補完なし、単一pending Occurrenceの方針をいずれも変更せずに、新しい繰り返し方を追加できる。
- 実装Issueは、この決定の候補列定義・入力制約・保存形式の候補を、そのままロジックと自動テストへ反映すればよい。

## 見直す条件

- Nか月ごと・N年ごとの固定間隔を追加する場合。暦月の長さが一定でないため、候補列の定義を新たに決める必要がある。
- 登録後に起点日や間隔を編集できるようにする場合。既存のpending Occurrenceを作り直すか、次回から新しい規則を適用するかを決める必要がある。
- 固定間隔に推奨期間(`deadline_kind = 'maintenance'`)を組み合わせる場合。
- 祝日・営業日補正など、候補列そのものを暦の都合でずらす機能を追加する場合。
- `task_rules`のCHECK制約をテーブル再作成で見直す機会がある場合。そのときは6の保存形式も併せて設計し直す。
