# YDR-051: 必達日を各回の予定・目安とは独立した暦日として持つ

## 背景と操作モデル

[#51](https://github.com/upu/YAMORU/issues/51)では推奨期間とは別に「この日までに必ず行う」を表す。利用者は各回に設定する方針を選んだ。家庭のメンバーはTodoの登録時、または未完了Todoの詳細で「今回の必達日」を設定・変更・解除できる。家庭共有の事実であり、本人だけの通知設定とは異なる。

## 決定

- `task_occurrences.must_complete_by`は任意の`YYYY-MM-DD`暦日。Asia/Tokyoの今日と比較し、必達日前・当日・超過を区別する。過去日も実際の期限として登録できる。存在しない日付は入力とDBで拒否する。
- Rule、scheduled_for、due_at、推奨期間を変更しない。予定が必達日より後でも勝手に補正せず、両方を表示する。延期、バックデート完了、訂正、取消でも元の必達日を維持する。
- すべての繰り返し方式に設定できるが、次のOccurrenceへはコピーしない。必要時Todoのscheduled_for/due_atは引き続きNULL。毎回の必達日を算出するRuleは今回追加しない。
- ホームでは必達日超過を最優先し、当日・7日以内も表示する。通常の推奨期間や予定日の状態も保持し、一つのTodoを重複表示しない。必達日がなく予定も未定なら従来どおりホームへ出さない。
- YDR-031とYDR-046の「予定日未定なら必ずホームへ出さない」という部分のみ、必達日がある回について置き換える。予定日のNULLペア、必要時の次回生成と延期禁止は維持する。
- 必達日の変更は専用の追記履歴へ本人・家庭・変更前後・記録日時を保存する。完了済み回は変更しない。画面が読んだ変更前値と一致しなければ競合として拒否する。
- 次回の必達日を設定してから解除した場合も操作履歴は残る。前回の完了取消・実施日訂正でその次回を削除・再計算することは拒否する。既存WorkerもDBのガードで同じデータ保護を受ける。

## 移行と保持

0030はnullable列、専用履歴テーブル、家庭一致の複合外部キー、日付制約、索引、旧経路の取消/訂正ガードを追加する。既存行・ID・timestamp・履歴は書き換えず、必達日はNULLとなる。新規登録はRule/Occurrence/必達日を同じbatchで保存する。変更履歴と更新も同じ条件付きbatchで成功または取消となる。家庭削除・Occurrence削除時の履歴はFKでcascadeするが、操作済み次回を完了取消で削除する経路は先に拒否する。

| 状態 | 読み書きと互換性 |
|---|---|
| 現Worker・現schema | 従来の予定と目安だけを扱う |
| 0030後・現Worker | 既存の列指定INSERT/UPDATEが継続。未設定はNULL。新しい履歴がある次回への危険な取消/訂正だけDBが拒否 |
| 0030後・新Worker | 必達日と専用履歴を読む/書く。家庭所属を毎回導出。旧Workerの更新でも必達日は保持 |
| 互換期間後 | contract migrationは不要。追加した列・履歴・ガードは恒久的に保持 |

旧Workerへ戻しても保存済み必達日は残るが、その画面には表示されない。修正は新しいmigration/Workerでforward fixし、0030の撤回や適用済みSQLの編集はしない。本PRからremote D1へ手動適用しない。

## 検証

新規DBと0029からの更新DB、旧SQL、日付制約、家庭A/B・非所属・未認証、途中失敗、競合、完了/次回生成/取消/訂正、設定後解除した次回の保護を実D1で確認する。日付境界とホームの優先、目安と必達日の併記、登録・詳細から設定/解除する操作をunitとE2Eで確認する。
