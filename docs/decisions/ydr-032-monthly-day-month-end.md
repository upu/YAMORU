# YDR-032: 毎月の定例日指定に「月末」を固定日1〜31とは別の意味として追加する

- 状態: Accepted
- 決定日: 2026-08-26

## 背景

[YDR-021](ydr-021-recurring-calendar-rules.md)は、毎月の日付指定(1〜31)で対象月に存在しない日付(29〜31日)をその月の月末日へ補正すると定めた。この規則により、「毎月31日」を指定すれば結果としてほぼ毎月末を表現できる。

一方、実利用では「31日に実施したい」のではなく「その月の最終日に実施したい」という意味を持つTodoがある([Issue #227](https://github.com/upu/YAMORU/issues/227))。例えば、月謝の支払いは利用者の意図として「毎月末」であり、「毎月31日」ではない。既存の31日指定は結果を近似できても、入力時に選んだ意味と保存された値がずれており、将来一覧や詳細を見返したときに「なぜ31日なのか」が伝わらない。

## 決定

### 1. 保存形式: 既存の固定日1〜31とは別の列で意味を区別する

- `task_rules`に`schedule_month_end`列(0/1のINTEGER、既定0)を追加する。`schedule_kind = 'monthly_day'`の月次日付指定に対してだけ意味を持つ。
- 「月末」を選んだ行は、`schedule_kind = 'monthly_day'`、`schedule_day_of_month = 31`、`schedule_month_end = 1`の組で保存する。31日は既存の月末補正規則によりどの月でも成立するため、この組み合わせだけが「月末」を表す。
- 上記以外の値で`schedule_month_end = 1`になることを、TRIGGERで拒否する(`schedule_kind`が`monthly_day`でない、または`schedule_day_of_month`が31でない場合)。
- 既存の`task_rules`のCHECK制約(`schedule_kind`ごとの列挙)は変更しない。0004で述べた「SQLiteでCHECK制約の列挙を安全に拡張する手段がない」という制約は今回も同じであり、テーブル再作成による拡張は行わず、`ALTER TABLE ADD COLUMN`と越境不変条件用のTRIGGERで表現する。

### 2. 暦計算: YDR-021の候補計算に変更を加えない

- 「月末」の候補計算は、既存の`schedule_day_of_month = 31`の候補計算(YDR-021の3)をそのまま使う。`schedule_month_end`列は候補日の計算に一切関与しない。
- そのため`src/lib/d1/calendar.ts`の暦計算ロジックはこの決定で変更しない。1月31日、2月28日/29日、4月30日など、月末日の算出は既存の「29〜31日が対象月に存在しない場合はその月の月末日へ補正する」規則がそのまま適用される。

### 3. YDR-013との関係

- [YDR-013](ydr-013-fixed-date-next-occurrence-calculation.md)は「月末や祝日調整など、暦上の予定枠自体を変更する機能を追加する場合」を見直す条件に挙げている。本決定はこの条件に該当する変更だが、YDR-013の次回予定枠の算出アルゴリズム(解決したOccurrenceの`scheduled_for`より後の最初の候補、候補が実際の解決日時以前である間さらに進める)自体は変更しない。
- 「月末」は暦上の候補系列そのもの(YDR-021の候補計算)を変えず、既存の31日指定の候補系列に意味のタグ付けをするだけであるため、YDR-013のアルゴリズムを変更する必要がない。次回Occurrenceも、遅延完了・バックデートの有無にかかわらず、YDR-013の規則へ既存の31日候補系列をそのまま渡せば正しく計算できる。
- したがって、この決定はYDR-013を置き換えない。YDR-013の見直し条件は、暦上の予定枠の算出方法自体を変える将来の変更(祝日調整など)のために残す。

### 4. 表示: 登録・詳細で「毎月末」と分かる

- Todo登録フォームの「毎月の日付」パターンに、「日付を指定」と「毎月末」のどちらかを選ぶ入力を追加する。「毎月末」を選ぶと、日付の入力は不要になる。
- Todo詳細では、定例日基準Todoの繰り返しパターンを表示する行を追加する。`schedule_month_end = 1`の行は「毎月末」、それ以外の`monthly_day`は「毎月N日」と表示する。

### 5. 対象範囲

- このIssueで「月末」を追加するのは毎月の日付指定(`monthly_day`)だけであり、毎年の月日指定(`yearly`)や毎月の第N曜日指定(`monthly_nth_weekday`)には追加しない。
- [Issue #100](https://github.com/upu/YAMORU/issues/100)で月次指定UIを統合する場合も、「日付で指定」の中で固定日と月末を選ぶという今回の構造をそのまま使える。

## 結果

- 「毎月31日」(固定日、意味は31日)と「毎月末」(月末、意味は最終日)を、保存・読み取りの両方で区別できる。
- 既存の31日指定の暦計算・自動テストに影響を与えず、月末専用の計算ロジックを新設する必要がない。
- 遅延完了やバックデート完了があっても、次回Occurrenceは既存のYDR-013・YDR-021の規則からそのまま導かれる。

## 見直す条件

- 月末について、既存の「29〜31日の月末補正」と異なる独自の暦計算(前営業日への繰り上げなど)が必要になった場合。
- 毎年の月日指定や毎月の第N曜日指定にも「月末相当」の指定を広げる必要が確認された場合。
- `task_rules`のCHECK制約(`schedule_kind`ごとの列挙)自体を、テーブル再作成を伴う形で見直す機会がある場合。そのときはこの決定の`schedule_month_end`列も併せて設計し直す。
