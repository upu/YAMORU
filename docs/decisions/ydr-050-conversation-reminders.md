# YDR-050: YAMORUが通知候補を決定し会話連携先へ届ける

- 状態: Accepted
- 決定日: 2026-10-17
- 関連: [#189](https://github.com/upu/YAMORU/issues/189)、#440〜#444
- 置き換える決定: [YDR-009](ydr-009-drop-notifications-consolidate-home.md)。通知を初期計画から外した経緯は保持し、v0.21.0では会話連携先一つへの通知を導入する。ホームの要対応表示は維持する。

## 背景

#189で利用者が会話操作と先回り通知を一体として計画することを選んだ。今回の変更根拠はこのプロダクト方針であり、YDR-009の見直し条件に挙げた家庭での実害を観測済みとするものではない。通知で防げた失敗や通知負担は導入後に評価する。

## 決定

1. YAMORUが期限・推奨期間・必達日・在庫から通知候補と理由を決定する。dotはその候補を説明し、許可された監視指示に沿って案内する。通知時刻と再通知をAIの記憶に依存させない。
2. 予定・実施履歴・在庫は家庭共有、接続先・時間帯・静かな時間・スヌーズ・mute・配信履歴は本人の設定とする。通知延期で期限を変えず、「予定を来週へ」は別の家庭共有操作として扱う。
3. 通知は初期状態では無効とし、本人が連携先と通知設定を選んで有効にする。必達日超過でも静かな時間を無断で迂回しない。監視の許可だけでTodoを自動完了しない。
4. 候補・outbox・配信履歴・leaseを永続化する。状態変更だけでなく日付の経過でも候補を再評価する。定期照合で取りこぼしを回収し、配信直前に完了・延期・所属・解除を再確認する。
5. MCP Eventsを第一候補とし、対象環境で認証、購読、署名、到達、解除を実証して有効にする。非対応環境では、利用者が設定した外部の定期実行が読み取りToolを呼ぶ方式を検証する。MCP Events自体のpolling機能と混同しない。実行主体が用意できない環境は会話での都度照会までとし、通知の完成条件を満たした扱いにしない。
6. イベント受領、会話での案内、利用者の既読を分ける。受領応答を既読と扱わない。重複・遅延・順序逆転・送信結果不明を前提に、照合可能なIDを保持する。即時配信や完全な一度だけの配信を保証しない。
7. 返答は通知に含まれた候補とOccurrenceへ結び付け、現在状態を読み直して[YDR-049](ydr-049-conversation-command-boundary.md)の共通操作へ渡す。失効、他の家族による完了、複数候補への曖昧な返答を区別する。
8. まずdotsへの連携を検証し、Push・メール・カレンダーなどの別チャネルは増やさない。Web画面のRealtime購読や家族の既読監視も追加しない。

## 結果

ホームを開かない時間にも案内できる一方、設定、永続配信、再接続、通知が来ない理由の説明が必要になる。[会話連携設計](../product/conversation-integration.md)で配信状態と検証条件を定義し、#444で実接続結果を確認する。未検証の接続能力を仕様上の保証にしない。

## 見直す条件

接続先の仕様変更、継続的な配信遅延、重複による負担、家庭データの過剰共有が判明した場合。別チャネル追加は実利用の必要性を評価して別の決定として扱う。
