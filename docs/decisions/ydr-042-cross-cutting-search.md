# YDR-042: 横断検索を名前一致で対象へ到達する常設機能として定義し、下部ナビゲーションの4項目目に置く

- 状態: Accepted
- 決定日: 2026-09-07

## 背景

YAMORUには現在、Todo一覧のTodo名検索([Issue #225](https://github.com/upu/YAMORU/issues/225)、[Issue #241](https://github.com/upu/YAMORU/issues/241))と、台帳の名前検索・詳しい種類での絞り込み([Issue #218](https://github.com/upu/YAMORU/issues/218)、[Issue #238](https://github.com/upu/YAMORU/issues/238)、[Issue #285](https://github.com/upu/YAMORU/issues/285))がある。どちらも「いま開いている一覧を絞り込む」操作である。

一方、家庭内で実際に使っていると、先に画面を選ばずに対象へ到達したい場面が出てきた。[Issue #284](https://github.com/upu/YAMORU/issues/284)でConsumableに「ある / 少ない / ない」の在庫状態を持たせた後、冷蔵庫を見て卵が少ないと気づいたときの操作は次のようになる。

```text
ホーム → 台帳 → 消耗品 → 卵を探す → 卵を開く → 在庫を「少ない」に変更する
```

このとき利用者は「消耗品一覧を見たい」のではなく、**対象が卵だと分かっているので名前から直接到達したい**。同じことは、名前だけ覚えている備品やTodoでも起きる。

`docs/product/yamoru-project-plan.md`は「検索」をMVP後の検討項目とし、モバイル下部ナビゲーションを「ホーム」「Todo」「台帳」の3項目としていた。この決定は、横断検索を実装対象へ引き上げるにあたって、その3項目方針を置き換える。ナビゲーションを扱った既存のYDRは無く、置き換える対象はプロダクト計画の記述である([Issue #242](https://github.com/upu/YAMORU/issues/242))。

## 決定

### 1. 画面内検索と横断検索の役割を分ける

| | 画面内検索 | 横断検索 |
|---|---|---|
| 目的 | いま開いている一覧を絞り込む | 画面を選ばず、名前から対象へ到達する |
| 対象 | その画面のエンティティ1種類 | Todo、ManagedItem、Consumable |
| 結果 | 同じ一覧の絞り込み結果(担当、状態、詳しい種類などの条件を保つ) | 種類ごとに分けた到達先の一覧 |
| 続きの操作 | 一覧上の操作(担当変更、完了など) | 詳細画面へ移動する |
| 入口 | 各画面の中(Todo一覧の虫眼鏡、台帳の検索・絞り込み) | 主要ナビゲーションの常設項目 |

- 横断検索は一覧の代わりにしない。大分類、詳しい種類、担当予定者、未完了 / 実施済みといった**条件による絞り込みは画面内検索の役割として残す**。横断検索が持つ条件は検索語だけとする。
- 画面内検索は現在の場所・現在の形のまま残す。共通ヘッダーへローカル検索の虫眼鏡を移さない。「いまの画面を探す操作」と「YAMORU全体を探す操作」を同じ位置に置かないためである。

### 2. 入口はモバイル下部ナビゲーションの4項目目とする

- モバイル下部ナビゲーションを「ホーム」「Todo」「台帳」「検索」の**4項目**にする(Issue #242の案1)。横断検索は独立した主要画面`/search`とする。
- プロダクト計画の3項目方針は、この決定で4項目へ変更する。日常的に使う到達手段は常設の入口が要り、補助メニューの奥(案3)では見つからないためである。
- 共通ヘッダーへ横断検索の虫眼鏡を置く案(案2)は採らない。Todo一覧の虫眼鏡(#241)と意味が重なり、モバイルでは同じ画面に虫眼鏡が2つ並ぶためである。
- PC向けサイドバー([Issue #219](https://github.com/upu/YAMORU/issues/219))を追加するときは、その4項目目として「検索」を置く。サイドバー導入前は、PCでも下部ナビゲーションの4項目をそのまま使う。
- 検索画面の状態はURLクエリー`?q=`で持ち、サーバー側で結果を描画する。戻る操作、再読み込み、共有で同じ結果になり、画面内検索(#218 / #225)と同じ規則になるためである。入力のたびに自動で検索せず、実行は明示操作とする。
- 狭い画面で4項目のラベルが折り返さないこと、既存のダイアログや追加ボタンと重ならないこと([Issue #156](https://github.com/upu/YAMORU/issues/156))は、実装Issueの受け入れ基準で確認する。

### 3. 初期の検索対象は3種類の「名前」に限る

初期対象は次の3つとする。

| 種類 | 検索するフィールド | 到達先 |
|---|---|---|
| Todo | TaskRuleの`title`(未完了のTaskOccurrenceを1件ずつ結果にする) | `/todos/{occurrenceId}` |
| ManagedItem | `name`(備品、サービス・契約) | `/managed-items/{id}` |
| Consumable | `name` | `/consumables/{id}` |

初期対象へ**含めない**フィールドと理由。

- Todoに関連するManagedItem名、Consumableに関連するManagedItem / Todo名: 名前が一致していない行が結果に出るため、「何に一致したか」を結果行で説明できない。関連元のManagedItemやTodo自体が結果に出るので、そこから関連をたどれる。
- ManagedItemの詳しい種類: 「種類」は絞り込みの語彙であり、台帳の絞り込み(#238)が担う。名前検索の結果へ種類一致を混ぜると、1つの入力欄が2つの意味を持つ。
- メモ、型番・品番: 一致箇所が名前と別の位置になるため、結果行に一致した断片を出す仕組みが要る。初期は「一致したのは常に名前」と決めることで、種類ラベルと名前だけで結果を説明できる形に留める。
- 実施済みTodo、実施履歴、家族の氏名・ニックネーム、外部リンク、添付ファイルの中身: 対象外とする。実施済みTodoは件数が増え続け、到達目的の検索とは別の「履歴を探す」操作になる。

対象フィールドを広げるのは、実利用での取りこぼしを確認し、結果行で一致箇所を説明できる形が決まってからとする。**何に一致したか説明できないまま対象を広げない。**

### 4. 検索結果は種類ごとに分けて表示する

- 結果は種類ごとのセクションに分ける。順序は「Todo」「備品」「サービス・契約」「消耗品」とし、台帳の入口の並び(#291)と揃える。一致が0件の種類はセクションごと出さない。
- 各セクションに件数を出す。行には名前と、種類が分かる表示を置く。
- 行の補助情報は種類ごとに次を出す。詳細へ入る前に、探していた対象かどうかを判断できるようにするためである。

| 種類 | 補助情報 |
|---|---|
| Todo | 予定日または期限 |
| 備品 / サービス・契約 | 詳しい種類 |
| 消耗品 | 在庫状態(ある / 少ない / ない) |

- Consumableは初期検索対象に**含める**。「卵」を探した利用者が詳細へ入る前に在庫状態を把握できるよう、在庫状態は検索結果の補助情報として表示する。ただし**在庫状態を検索条件にはしない**(在庫で絞る操作は買い物候補と消耗品一覧が担う)。
- 行から移動するのは対象の詳細画面だけとする。検索結果から在庫状態を直接変更するクイック操作は初期実装で作らない。

### 5. 一致の規則、0件、件数上限

- 一致は部分一致とする。前後の空白を無視し、ASCIIの大文字・小文字を区別しない。既存の`src/lib/d1/text-search.ts`(`likeSearchPattern`)をそのまま使い、`%`と`_`は検索語として文字通り扱う。
- ひらがな / カタカナ、全角 / 半角、送り仮名の表記揺れは初期は吸収しない。SQLiteの標準機能では正規化できず、正規化用の列を持つと更新経路が増えるためである。
- 検索語が空、または空白だけのときは0件表示にせず、入力を促す案内を出す。1文字から検索する(日本語は1文字が意味を持つ)。
- 0件のときは、検索語を示したうえで、Todo一覧と台帳の各入口へのリンクを出す。「見つからない = 登録されていない」と決めつけない。
- **件数上限は種類ごとに20件**とする。取得は`LIMIT 21`で行い、21件目が返ったかどうかで「まだ結果がある」を判定する。総件数の`COUNT(*)`は数えない(既存の`CONSUMABLE_CANDIDATE_LIMIT`と同じ考え方)。1回の検索でD1から読む行数は3種類 × 21件 = 63行に固定される。
- 上限に達した種類には「先頭の20件を表示しています。語を足すと絞り込めます」と案内する。ページング(次ページ、無限スクロール)は初期実装で作らない。家庭1つあたりの対象は数百件程度で、語を足せば十分絞れるためである。
- SQLite FTS(FTS5)は初期は導入しない。`LIKE '%語%'`は先頭ワイルドカードのため索引が効かず走査になるが、走査対象は`household_id`で絞った1家庭分であり、想定件数ではD1で足りる。FTS5は同期用トリガーとマイグレーションを増やし、日本語では既定のトークナイザがCJKを分割しないという別の問題を持ち込む。

### 6. 家庭単位の認可を候補・件数・結果・遷移で維持する

- 3種類のクエリーはすべて`requireCurrentHouseholdId`を通し、`WHERE household_id = ?1`を最初の条件に置く(`src/lib/d1/`の既存クエリーと同じ)。
- 件数、上限判定(21件目の有無)、セクションの有無も家庭内のデータだけで決まる。他家庭の対象は結果にも件数にも「まだ結果がある」の判定にも現れない。
- 結果から移動した先の詳細画面は、既存の家庭単位の認可をそのまま通る。他家庭のIDを直接指定した場合の挙動は現在と変わらない。
- 他家庭のデータに一致する検索語でも何も現れないことを、`src/lib/d1/**/*.d1-test.ts`の家庭間分離テストで確かめる。

### 7. お気に入り(#345)との役割分担

- **お気に入り**: 日常的によく触る少数の対象への最短導線。ホームに常設し、入力なしで見える。
- **横断検索**: お気に入り外も含めた全対象への汎用的な導線。入力してから到達する。
- ホームのお気に入り一覧に検索欄を置かず、横断検索の結果にお気に入り登録操作を置かない。同じ目的のUIを二重に作らないためである。
- [Issue #345](https://github.com/upu/YAMORU/issues/345)で在庫状態のクイック変更が有効だと分かった場合に、それを検索結果へ広げるかは別途決める。

### 8. この決定で扱わない範囲

- AIによる意味検索、外部検索サービス、ベクトル検索。
- 添付ファイル、PDF、画像内テキストの検索。
- 家庭をまたぐ検索、家庭外への共有。
- 検索履歴、検索候補のサジェスト、最近見た対象の表示。
- 検索結果からの一括操作、並び順の利用者ごとのカスタマイズ。
- 消耗品・在庫機能自体の再設計。

## 結果

- 利用者は、対象の種類を先に選ばずに名前で探せる。卵の在庫更新は「検索 → 卵 → 在庫を変更」に短くなる。
- 「いまの画面を絞り込む」と「YAMORU全体から探す」が、別の入口・別の結果の形として区別される。
- 結果に出る行は常に名前が一致した行なので、種類ラベルと名前だけで「なぜこの行が出たか」を説明できる。
- 1回の検索でD1から読む行数が上限で固定されるため、家庭内の対象が増えても取得量と応答時間の上振れが起きない。
- プロダクト計画の下部ナビゲーションが3項目から4項目へ変わる。#219のPC向けサイドバーも4項目を前提にする。

## 見直す条件

- 名前一致だけでは実利用で対象へ到達できない例が溜まった場合。3の初期対象フィールドと、結果行での一致箇所の示し方を決め直す。
- 1家庭の対象が数千件を超え、検索の応答時間が実測で目標を超えた場合。5のFTSを導入しない判断を見直す。
- 種類ごと20件の上限で「まだ結果がある」案内が日常的に出るようになった場合。ページングの要否を決め直す。
- 4項目の下部ナビゲーションが狭い画面で使いにくいと分かった場合。2の入口の置き方を決め直す。
- #345のお気に入りが日常操作を十分に賄い、横断検索の利用が伸びない場合。7の役割分担と、横断検索を常設項目に置く判断を見直す。
