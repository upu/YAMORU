# YDR-019: 家族招待の発行・受諾・失効ライフサイクルを固定する

- 状態: Accepted
- 決定日: 2026-08-14

## 背景

Phase 0の招待受諾スパイク([#20](https://github.com/upu/YAMORU/issues/20)、[招待トークン受諾とRLSによる家庭間分離の技術スパイク](../spikes/household-invitation-acceptance.md))は、期限付き・一回限りの招待トークンを認証済み利用者が安全に受諾し、受諾後もRLSによる家庭間分離を維持できることをDB層で検証した。一方、招待の発行方法、招待先メールとの一致、有効期限、取消・再発行、未ログイン時の復帰、試行回数制限はスパイクの対象外として残された(スパイク文書「残るリスクと後続実装への注意点」)。

これらはセキュリティと利用者体験の両方にまたがる契約であり、個別の実装Issueで暗黙に決めると、実装ごとに異なる前提が生まれる。Phase 2の実装に入る前に、これらを一つのYDRとして固定する。

## 決定

### 発行方法

- アプリ内で招待リンクを生成し、利用者が手動でコピー・共有する。アプリからのメール送信機能は持たない。
- 家庭メンバー全員(Owner / Memberの区別を設けない、[YDR-005](ydr-005-no-realtime-no-fine-grained-permissions.md)と整合)が招待の発行・取消・再発行を同じ権限で行える。

### 招待先メールとの一致

- 招待発行時に招待先メールアドレスを指定する。
- 受諾は、Authが保証する受諾者のメールアドレスが招待先メールアドレスと一致する場合に限り成立する。比較は、Authが確認済みの受諾時点の現在のメールアドレスに対して行う(招待発行後にメールアドレスが変更されていれば現在値と比較する)。大文字小文字を区別せず、前後の空白を除去して比較する。
- 不一致は無効なトークンと同じ扱いとし、下記「受諾エラーの扱い」の共通エラーに含める。

### 有効期限と一回性

- 招待は発行から7日間有効。
- 受諾は一回限りで、成立後は同じ招待を再び受諾できない。

### 取消・再発行

- 家庭メンバーは招待を取消できる。取消後、旧リンクは即時に無効化される。
- 再発行(同じ招待先メールへ新しい招待を作る、または期限切れ招待をやり直す)では、新しいトークンを発行し、同じ招待先メールに対する未使用の旧招待を即時に無効化する。同じ招待先メールに対して同時に有効な招待は常に高々1件とする。これはIssue #20のスパイクが扱わなかった、本YDRで新たに定める制約である。
- 取消・再発行はいずれもDB層で旧トークンを使用不可にする操作を伴う。旧リンクを開いた利用者には、下記「受諾エラーの扱い」と同じ共通エラーを返す。
- 同一招待に対して受諾・取消・再発行が同時に発生した場合は、DB側で直列化し、最初にcommitされた一つの結果だけを成立させる。失敗した操作は招待やmembershipの状態を変更しない(スパイクが検証した、部分更新をしない原則を踏襲する)。

### 未ログイン時の受諾

- 未ログインで招待リンクを開いた利用者は、登録・ログイン・(未登録なら)ニックネーム登録([YDR-018](ydr-018-account-nickname-as-member-display-name.md))を経て、招待の受諾へ戻る。
- 生の招待トークンをURLに含めたまま認証フローを回さない。招待リンクへの最初の到達時に、生トークンをサーバー管理の一時状態(有効期限付き)へ交換し、以後はトークンを含まないURL(一時状態を指す不透明な参照)で認証フローを進める。
- 一時状態を指す参照は、生の招待トークンと同様の秘密情報として扱う。十分な乱数強度を持たせ、単回使用とし、Refererでの送出やログへの記録を避ける。
- 一時状態の有効期限は、招待自体の残り有効期限を超えない。

### 一人一家庭制約下での受諾結果

一人一家庭制約は、[#28](https://github.com/upu/YAMORU/issues/28)で追加された`household_members.user_id`のunique制約による([YDR-018](ydr-018-account-nickname-as-member-display-name.md)もこの制約を前提にしている)。受諾者が既にいずれかの家庭に所属している場合の応答は、次の一点だけを条件とする不変条件として定める。

- **トークンが有効であり、かつ招待先が受諾者の所属家庭と一致する場合に限り**、受諾は成功として扱い、重複membershipを作らない(スパイクの既存動作を踏襲)。利用者には失敗ではなく「既にこの家庭のメンバーである」という結果を明示する。この結果は、正当な招待(有効なトークン)を持つ利用者にしか返らないため、招待の存在や状態を外部に漏らさない。
- **それ以外の場合**(トークンが無効・期限切れ・使用済み・取消済み・メール不一致である場合、または招待先が受諾者の所属家庭と異なる場合を含む)は、常に同一の「既に別の家庭に所属しているため参加できない」エラーを返す。トークンの状態によって内容や有無を変えない。
- 家庭メンバーへ表示する招待一覧では、未使用・受諾済み・期限切れ・取消済み・再発行済み(=旧招待)の状態を区別して表示する。

### 受諾エラーの扱いと試行制限

- 招待を開いた利用者(受諾者)には、無効・期限切れ・使用済み・取消済み・メール不一致のいずれであっても、招待の存在や状態を推測しにくい共通エラーを返す。この「共通」は、レスポンス本文だけでなく、HTTPステータス、アプリ内エラーコード、リダイレクト先、応答時間を含むレスポンス全体で区別できないことを指す。失敗種別による早期リターンで処理時間に差が出ないようにする。
- 上記「一人一家庭制約下での受諾結果」の別家庭所属エラーは、招待側の情報ではなく受諾者自身の状態に関する情報であり、成功条件を満たさない限りトークンの状態によって内容や有無が変わらないため、この共通エラーの原則を破らない。
- 受諾試行には、トークンの有効・無効を問わずすべての試行に対して、IPアドレス(未認証時)およびアカウント単位(認証後)のレート制限を設ける。無効なトークンの試行だけを対象にすると、レート制限の発火自体がトークンの有効性を示すオラクルになるため、有効なトークンによる試行も同じ制限対象に含める。レート制限に達した場合の応答も、上記の共通エラーと区別できない形にする。
- レート制限はWeb/API層で行い、受諾そのものを行うDB関数(RPC)の責務には含めない(スパイク文書「残るリスクと後続実装への注意点」の想定を踏襲する)。
- セキュリティログには、生の招待トークン、一時状態を指す生の参照、招待先メールアドレスの本文、認証トークンなどの秘密情報を残さない。招待IDのようなハッシュ後・非秘匿の識別子、結果種別、レート制限に必要なIPアドレスやアカウント識別子は記録してよい。

## 結果

- Phase 2の招待実装(発行UI、受諾UI、ログイン復帰、DB関数の拡張)は、本YDRの契約に従う。
- スパイクで採用した`SECURITY DEFINER`のRPC方式は、メール一致確認・所属状態に応じた結果分岐・取消/再発行時の旧トークン無効化・受諾/取消/再発行の直列化に対応するよう拡張が必要になる。試行回数のレート制限はRPCではなくWeb/API層で扱う(上記「受諾エラーの扱いと試行制限」節)。これらの実装は実装Issueで扱う。
- 招待の状態(未使用・受諾済み・期限切れ・取消済み・再発行済み)を判別するためのカラムまたは仕組みがスキーマに必要になる。

## 見直す条件

- Owner / Memberなど役割区別を導入する。その時点で「全メンバーが同権限で招待を管理する」前提を再設計する。
- 複数家庭対応を導入する。その時点で一人一家庭制約に依存する受諾結果の扱いを再設計する。
- アプリからの招待メール送信を導入する。その時点で手動共有前提を再設計する。
- Googleログインなど、Authが保証するメールアドレスの性質が変わる認証方式を追加する。
