# YDR-023: 公開登録を閉じ、招待限定のアカウント作成と最小のパスワード運用を採用する

- 状態: Superseded by [YDR-024](ydr-024-invitation-token-in-url-fragment.md)(「招待トークンは推測困難な乱数とし…生トークンを含むURLは最初のサーバー到達後にブラウザーのアドレス欄から取り除き…」の搬送方式のみ置き換え。招待の発行・失効ライフサイクル、7日間・一回限り・メール一致の契約、共通エラー、パスワード運用など、他はすべて[YDR-024](ydr-024-invitation-token-in-url-fragment.md)でも維持される)
- 決定日: 2026-08-20
- 置き換える決定: [YDR-019](ydr-019-invitation-lifecycle.md)の全体。本YDRは、継続する招待契約を含めてAuth.js Credentials向けに再定義する。

## 背景

[YDR-022](ydr-022-cloudflare-workers-d1-migration.md)は、本番認証をSupabase AuthからAuth.js Credentials(メールアドレスとパスワード)+JWTセッションへ移行する方針を採用した。一方、YDR-019は「Authが確認済みのメールアドレスと招待先メールアドレスの一致」を受諾条件としており、メール所有確認を行わないCredentials認証へそのまま適用できない。

YAMORUは一般公開サービスではなく、自分の家庭で使う家族専用アプリとして運用する([プロダクト計画](../product/yamoru-project-plan.md)のプロダクト原則7)。そのため、公開登録やメールによるアカウント回復を追加するより、初回利用者と招待された家族だけがアカウントを作成できる小さな運用境界を明確にする。

## 検討した案

- **案1(採用): 初回bootstrap + 招待限定登録**。公開signupを持たず、運用者による一回限りのbootstrapと有効な招待だけをアカウント作成経路にする。家族専用運用に必要な範囲へ実装と攻撃面を絞れる一方、メール所有確認とセルフサービスのパスワード回復は提供できない。
- 案2: メール確認とパスワードリセットメールを自前で実装する。一般利用者には馴染みやすいが、メール送信基盤、到達性、トークン管理、運用監視が必要になり、家族専用運用には過剰である。
- 案3: Googleなどの外部IdPを使う。メール所有確認と回復をIdPへ委ねられるが、外部サービスへの依存と複数認証方式の管理が増える。

## 決定

### アカウント作成経路

- 通常のログイン画面、公開ページ、公開APIにはsignup経路を設けない。招待情報を持たない要求から利用者を作成できるサーバー処理も設けない。UIを隠すだけでは公開signupの封鎖とみなさない。
- 新しいアカウントを作成できる経路は、最初のアカウントを作る管理用bootstrapと、有効な招待を使う登録の二つだけとする。
- アカウントのメールアドレスはログイン識別子として保存し、大文字小文字を区別せず、前後の空白を除去した正規化値を一意に扱う。MVPではメールアドレス変更を提供しない。

### 最初のアカウントのbootstrap

- 最初のアカウントは、運用者がローカルから明示的に実行する管理コマンドで作成する。公開Web画面、公開API、デプロイ時の自動処理からは実行できないようにする。
- bootstrapは利用者が一人も存在しない場合だけ成功する一回限りの操作とする。既に利用者が存在する場合は何も変更せず失敗する。
- bootstrapが作るのは、ログインに必要な利用者レコードとパスワードハッシュまでとする。成功後は通常どおりログインし、[YDR-018](ydr-018-account-nickname-as-member-display-name.md)のニックネーム登録と最初の家庭作成を既存のオンボーディングで行う。
- メールアドレスと初期パスワードはリポジトリ、設定ファイル、シェル履歴、プロセス一覧、アプリケーションログへ残さない。パスワードは対話入力または標準入力など、コマンドライン引数へ平文を置かない方法で受け取り、平文を保存せず、適切なpassword hashだけをD1へ保存する。
- 管理コマンドの実行に必要なCloudflare認証情報や接続情報は、リポジトリへ保存せず、Cloudflareが提供する秘密情報または運用者のローカル認証状態として扱う。

### 招待の発行とライフサイクル

- アプリ内で招待リンクを生成し、家庭メンバーが家族へ手動で共有する。アプリからの招待メール送信機能は持たない。
- 家庭メンバー全員が招待の発行・取消・再発行を同じ権限で行える。Owner / Memberの役割は設けない。
- 招待発行時に招待先メールアドレスを指定する。招待は発行から7日間有効で、一回限り使用できる。
- 家庭メンバーは未使用の招待を取消できる。取消後、旧リンクは即時に無効とする。
- 同じ家庭・同じ正規化済み招待先メールアドレスへ再発行するときは、未使用の旧招待を即時に無効化する。同時に有効な招待は高々1件とする。
- 招待トークンは推測困難な乱数とし、D1には生トークンではなく照合用のhashだけを保存する。生トークンを含むURLは最初のサーバー到達後にブラウザーのアドレス欄から取り除き、以後の登録・ログイン復帰に必要な継続状態は`Secure`、`HttpOnly`、`SameSite`属性を持つ短命なCookieなどのサーバー管理下の方法で保持する。生トークンや継続状態をログ、分析イベント、Refererへ残さない。

### 招待リンク、メールアドレス、本人性の意味

- 招待リンクを所持していることを、その家庭が家族へ渡した招待を行使する権限の根拠とする。家族へリンクを渡す共有経路は、招待を発行した家庭メンバーが信頼する。
- 招待先メールアドレスと登録または既存アカウントのメールアドレスは、同じ正規化規則で一致しなければならない。この一致は、招待対象と作成・参加するアカウントを結び付け、誤ったアカウントでの受諾を防ぐために使う。
- YAMORUは確認メールを送らないため、上記の一致は、そのメールボックスを利用者が所有・管理していることの証明ではない。アカウントのメールアドレスも、本人性が外部で確認済みであることを意味しない。
- 招待リンクを転送・漏えいした者は、招待先メールアドレスを知っていれば、その家族になりすまして有効期限内にアカウントを作成できる。この残存リスクを、家族専用の手動共有運用として受け入れる。

### 招待からの登録と参加

- 未登録の利用者は、有効な招待の継続状態からだけ、招待先と一致するメールアドレス、ニックネーム、パスワードを設定してアカウントを作成できる。
- 新規利用者の登録では、利用者レコードとpassword hashの作成、`profiles`の作成、対象家庭のmembership作成、招待の使用済み化を一つのD1トランザクションとして成立させる。いずれかが失敗した場合は全体を取り消し、利用者だけ、profileだけ、membershipだけが残る部分状態を作らない。
- 既存利用者は新しいアカウントを作らず、招待先と一致するアカウントでログインして参加する。membership作成と招待の使用済み化を一つのD1トランザクションとして成立させる。
- 有効な招待の対象家庭へ既に所属している場合は、重複membershipを作らず冪等に成功し、招待を使用済みにする。別の家庭へ所属している場合は失敗し、membershipと招待の状態を変更しない。一人一家庭制約は継続する。
- 同一招待に対して登録・受諾・取消・再発行が同時に行われても、最初にcommitされた一つだけを成立させる。他の操作は部分状態を残さず失敗する。

### エラー、試行制限、セキュリティログ

- 招待を開いた利用者には、招待が無効、期限切れ、使用済み、取消済み、メール不一致のいずれであっても、招待の状態を詳しく示さない共通エラーを返す。レスポンス本文、HTTPステータス、アプリ内エラーコード、リダイレクト先を失敗種別で分けない。
- 家庭メンバー向けの招待一覧では、自分の家庭が発行した招待について、未使用・受諾済み・期限切れ・取消済み・再発行済みを区別して表示してよい。
- MVPでは、YDR-019が求めた応答時間の均一化と、招待の有効・無効を問わずIPアドレス・アカウントの双方へ同じ制限をかける招待専用の試行制限は実装しない。推測困難で短命・一回限りのトークン、手動共有、共通エラー、Cloudflareの一般的な濫用対策を境界とし、家庭内運用で実害または継続的な不正試行が観測された場合に強化する。
- 認証・招待のログには、パスワード、生のpassword hash、生の招待トークン、継続状態、JWT、招待先メールアドレスの本文、Cloudflareの秘密情報を残さない。非秘匿の招待ID、結果種別、利用者IDなど、運用に必要な最小限の識別子だけを記録する。

### パスワードの設定・変更・回復

- パスワードの初回設定は、bootstrapまたは招待登録の中だけで行う。平文を保存・ログ出力せず、password hashだけを保存する。
- ログイン中の利用者は、現在のパスワードを再確認した場合だけ新しいパスワードへ変更できる。変更時はpassword hashを置き換え、既存のJWTセッションを失効できる利用者単位のバージョンを更新する。変更を行ったセッションを含め、新しいパスワードで再ログインする。
- 「パスワードを忘れた」利用者向けのセルフサービス回復、回復メール、秘密の質問は提供しない。運用者がローカルの管理コマンドで対象利用者のパスワードを再設定する。
- 再設定コマンドもパスワードをコマンドライン引数、設定ファイル、ログへ残さず、password hashの置換と既存JWTセッションの失効を一つの操作として行う。対象利用者が一意に特定できない場合は何も変更せず失敗する。

## 結果

- 公開signup、招待登録、初回bootstrap、パスワード変更・回復の境界が一つの決定から読める。
- メールアドレスはログイン識別子と招待対象の照合値であり、確認済み本人情報ではない。
- #121は、D1の一意制約、トランザクション、利用者単位のセッションバージョンなど、この契約を実現できるデータ層の土台を用意する。
- #122は、Auth.js、管理コマンド、ログイン、招待登録、パスワード変更・再設定を本YDRに従って実装する。
- メール配信基盤と一般公開向けの回復機能を持たない代わりに、招待リンクの安全な共有と運用者による回復が必要になる。

## 見直す条件

- 家族以外を含む一般公開signup、複数家庭、Owner / Memberなどの役割を導入する。
- メール送信基盤またはGoogleなどの外部IdPを導入し、メール所有確認やセルフサービス回復を提供する。
- 招待リンクの漏えい、不正なアカウント作成、継続的な総当たり試行が観測される。その場合は、招待専用の試行制限、監査ログ、追加の本人確認を再検討する。
- 管理コマンドによるbootstrapまたはパスワード回復が、日常運用上の負担または可用性リスクになる。
