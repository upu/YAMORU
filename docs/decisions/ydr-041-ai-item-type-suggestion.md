# YDR-041: 詳しい種類のAI提案を明示操作の入力補助に限定し、提案と採用結果を家庭内へ記録する

- 状態: Accepted
- 決定日: 2026-09-05

## 背景

[YDR-028](ydr-028-managed-item-kind-item-type-tags.md)は、ManagedItemの大分類・詳しい種類・タグの役割を分けた。詳しい種類はプリセットからの選択と自由入力の両方を許すため自由度が高く、対象名だけを見ても利用者が毎回適切な表現を考える必要がある。

[Issue #288](https://github.com/upu/YAMORU/issues/288)で、同じ家庭ですでに使われている自由入力の詳しい種類を候補として再利用できるようにした。それでも、家庭内にまだ前例がない対象や、入力途中の情報からより適切な種類を考えたい場合には、利用者自身が判断する必要が残る([Issue #332](https://github.com/upu/YAMORU/issues/332))。

一方[YDR-008](ydr-008-ai-not-source-of-truth.md)は、AIを正しさの基盤にしないことを決めており、AIを導入する場合の条件として「AIの出力を人が確認する明確なフローと、誤りが基幹データへ直接影響しない設計がある」ことを挙げている。この決定は、YDR-008を置き換えるものではなく、その条件を満たす最初の具体化として、詳しい種類のAI提案が守るべき境界を定める。

## 決定

### 1. AIの役割は候補の提示に限る

- AIは詳しい種類を**確定しない**。提示するのは候補だけで、最終的な値は常に利用者が選ぶ。
- AI提案は自動実行しない。入力のたびに問い合わせず、利用者が提案ボタンを押したときだけ実行する。
- 大分類、タグ、Todo、消耗品をAIが決めることはこの決定の範囲に含めない。詳しい種類だけを対象とする。
- 候補を採用した結果は、既存フォームの保存形式(プリセットの`item_type_code`、または自由入力の`custom_item_type`)へそのまま入れる。AI専用の分類値や「AI由来」を表す台帳側の列は作らない。台帳を読む側から見て、AIを使った登録と使わない登録は同じ形で保存される。

### 2. AIへ渡す情報の範囲

提案の文脈に使うのは次の3種類に限る。

- **入力中の情報**: 管理対象名、選択中の大分類、詳しい種類の入力途中の値、メーカー・商品名、メモ。ボタンを押した時点の値をそのまま使い、未入力の項目を待たない。未入力の項目は文脈から省く。
- **同じ家庭の既存データ**: 選択中の大分類で使用中の自由入力の詳しい種類(#288と同じ取得・正規化)、選択できるプリセットの詳しい種類、その家庭の過去の提案と採用結果。
- **YAMORU専用知識**: 家庭用品・サービスの代表的な種類、その言い換え、メーカー名などの関連語。少量の構造化データ(TypeScript定数)として持つ。ベクトルDBや大規模RAG基盤は前提にしない。

制約として次を守る。

- 他家庭の個別データを提案の文脈へ混ぜない。家庭内データの取得はすべて`household_id`で絞り込む。
- 送信は必要最小限にする。外部リンク、家族の氏名やニックネーム、Todoや実施履歴はAIへ渡さない。メモは全文ではなく先頭のみを渡す。
- YAMORU専用知識は、入力中の情報と一致した項目だけを渡す。一致が無ければ知識を渡さない。

### 3. 家庭内の既存表記を優先する

- 家庭内にすでに同じ意味の表記がある場合は、新しい言い方を作らず既存の表記を返す。表記の一致判定には、一覧の絞り込み・#288の候補選択と同じ正規化(前後の空白と大文字小文字を無視する)を使う。
- 候補は最大3件までとする。重複、空文字、詳しい種類の上限(50文字)を超える値は捨てる。
- AIの返答から候補を読み取れない場合は、文章を推測で候補へ変えず「候補なし」として扱う。

### 4. 提案と採用結果を区別して記録する

- 記録の単位は「1回の提案要求」とする。提案した候補と、その提案が画面に出ている状態で最終的に採用された詳しい種類を、同じ行に持つ。
- 採用結果は次の2種類だけを記録する。

| 操作 | 記録 |
|---|---|
| AI候補をそのまま採用 | `ai_suggestion`(肯定) |
| AI候補とは別の既存種類・自由入力を採用 | `corrected`(修正) |
| AI候補を閉じただけ | 記録しない |
| AIを使わず登録 | 記録しない |
| 詳しい種類を指定せずに登録 | 記録しない |

- 「AIが提案したが採用されなかった」ことだけを否定として記録しない。記録するのは**最終的に何が採用されたか**であり、採用結果が無い行は学習材料として読まない。
- 採用結果は1回だけ書き、後から上書きしない。提案IDが自家庭のものでない場合は何も書かない。
- 採用されたプリセットは、コードではなく表示ラベルで記録する。自由入力・既存の種類と同じ土俵で次回の提案へ渡すためである。
- 記録は入力補助の履歴であり、台帳の正本ではない。記録に失敗しても登録・編集そのものは成功として扱う(YDR-008)。

### 5. 次回の提案への反映

- 反映はモデルの再学習ではなく、**次回リクエストの文脈**として行う。同じ家庭・同じ大分類の採用履歴を、提案と採用結果の対のまま渡す。
- 複数家庭の採用結果を匿名化・集約してYAMORU共通知識へ還元することは行わない。プライバシー、誤学習、品質管理を別途検討する必要があるため、必要になった時点で別の決定とする。

### 6. AIが使えないときの挙動

- Workers AIのバインディングが無い環境、呼び出しの失敗、時間切れ、候補を読み取れない返答のいずれでも、画面には案内文を出すだけとする。
- どの場合でも、これまでの手動入力とYDR-028以来のプリセット選択、#288の家庭内候補選択はそのまま使える。AI提案は登録・編集の前提条件にしない。
- 待ち時間は上限を設ける。待たされるくらいなら手入力を続けられた方がよいため、時間切れは「候補を出せなかった」として扱う。

### 7. 実装上の選択

- AIの実行基盤はCloudflare Workers AIのバインディングを使う([YDR-022](ydr-022-cloudflare-workers-d1-migration.md)でWorkersを採用しているため、追加の秘密情報を持たずに呼べる)。
- バインディングを置くのはpreviewとproductionだけとする。Workers AIにはローカルエミュレーションが無く、既定(local)やE2E環境へ置くとビルドと開発サーバーがCloudflareへのremote接続とAPI tokenを要求するためである。local開発とローカルE2Eは6の「AIが使えないとき」の経路をそのまま通る。
- ベンダー、モデル、検索基盤を先に抽象化しない。差し替えが必要になった時点で、呼び出し口(`src/lib/ai/`)だけを変える。
- 提案文脈の組み立てと返答の解釈は、AI呼び出しから切り離した純粋な処理として持ち、自動テストで確かめる。

### 8. この決定で扱わない範囲

- AIによる大分類・タグの自動確定、Todoや消耗品の自動作成。
- AI提案だけで登録内容を自動保存すること。
- 複数家庭の個別データの共有、全家庭の結果からのYAMORU標準知識の自動更新。
- モデルのファインチューニング、独自学習基盤、ベクトルDBや大規模RAG基盤。
- 提案の利用回数・費用の上限管理。

## 結果

- 利用者は、詳しい種類に迷ったときだけ候補を求められる。押さなければAIは動かず、費用も発生しない。
- AIが誤った候補を出しても、台帳へ入るのは利用者が選んだ値だけであり、基幹データへ直接影響しない。YDR-008の見直し条件を満たす形になる。
- 家庭が候補を修正した結果が次回の提案へ渡るため、家庭ごとの言い方へ寄っていく。他家庭のデータは混ざらない。
- AIを使えない環境でも、登録・編集の機能は#288までと同じまま動く。

## 見直す条件

- 少量の構造化知識では候補の質が足りないと分かった場合。検索基盤の高度化(2の前提)を見直す。
- 家庭内の採用履歴だけでは提案が改善しないと分かった場合。5の「文脈として渡す」方式の見直しが要る。
- 詳しい種類以外(大分類、タグ、Todo)へAI提案を広げる場合。1の範囲を決め直す。
- 提案の利用回数や費用が問題になった場合。上限管理を8から範囲へ入れる。
- Workers AI以外の実行基盤へ移す場合。7の「抽象化しない」判断を見直す。
