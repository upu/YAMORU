# YDR-021: 定例日基準Todoの暦規則とタイムゾーンを固定する

- 状態: Accepted
- 決定日: 2026-08-14

## 背景

#50の定例日基準Todo(毎週の曜日、毎月の日付、毎月の第N曜日、毎年の月日)は、存在しない月日、第5曜日がない月、2月29日、タイムゾーンの規則が未決である。これらを実装内だけで決めると、YDR-013の次回Occurrence計算や将来の月・年単位周期と矛盾しやすい。

Phase 1の完了日基準オフセット計算(`complete_maintenance_task`)は、家庭のタイムゾーンをAsia/Tokyo固定として既に実装している(`app/time-zone.ts`の`PHASE_ONE_TIME_ZONE`)。この決定は、その前提を定例日基準の暦計算にも明示的に拡張する。

## 決定

### 1. 家庭暦とタイムゾーン

- Phase 2でもMVPの家庭タイムゾーンはAsia/Tokyo固定とする。家庭ごとのタイムゾーン変更UIは扱わない(#50のPhase 2の境界に従う)。Asia/TokyoはDSTを持たないため、夏時間切り替えによる暦日のずれを考慮する必要がない。
- 定例日基準の暦上の候補は、Asia/Tokyoの暦日で判定する。`scheduled_for`(timestamptz)は、該当する暦日のAsia/Tokyo 00:00を表す瞬間として計算する。これは`complete_maintenance_task`が完了日基準オフセットで使う`(date)::timestamp at time zone 'Asia/Tokyo'`と同じ変換であり、UTCの日付境界では判定しない。

### 2. 存在しない月日の補正

- 毎月の日付指定(29〜31日)が対象月に存在しない場合、その月の月末日へ補正する。
- 例: 「毎月31日」ルールの4月の候補は4月30日、2月の候補は2月28日(平年)または2月29日(うるう年)。
- この補正は月自体をスキップしない。対象月に必ず1件の候補を生成する。

### 3. 毎年の月日指定とうるう年

- 毎年の月日指定が2月29日の場合、うるう年でない年の候補は2月28日へ補正する。
- 2月29日以外の月日指定は、存在しない年が生じないため補正対象外とする。
- 例: 「毎年2月29日」ルールの候補は、2028年(うるう年)は2月29日、2029年(平年)は2月28日。

### 4. 存在しない第N曜日

- 毎月の第N曜日指定(第5曜日を含む)で、対象月にその第N曜日が存在しない場合、その月の候補を生成せず、次に第N曜日が成立する月まで候補を進める。
- 第4曜日など、より若い週へ繰り下げる補正は行わない。
- 例: 「毎月第5月曜日」ルールで、ある月に第5月曜日がない場合、その月は候補を持たず、次に第5月曜日が存在する月の当該日が次回候補となる。
- 毎週の曜日指定は、どの週にも対象の曜日が存在するため補正・スキップの対象にならない。

### 5. YDR-013の次回計算との整合

- 次回候補の探索は、上記2〜4で補正・スキップ済みの暦上の候補系列に対してYDR-013の規則をそのまま適用する。すなわち、最初の候補は解決したOccurrenceの`scheduled_for`より後にある最初の(補正済み)候補とし、候補が実際の解決日時(完了時は`occurred_at`、スキップ時は操作日時)以前である間、次の(補正済み)候補へ進める。
- 上記2〜4の補正・スキップ後の候補系列は、暦上厳密に単調増加する(同じルールが同じ月・年に2件以上の候補を生成することはない)。したがって`(task_rule_id, scheduled_for)`の一意制約(YDR-012)は、補正・スキップを導入しても壊れない。
- 定例日基準ルールの最初のOccurrence生成(#50で実装)にも、同じ補正・スキップ規則を適用する。ルール登録日以降で最初に成立する(補正済み)候補を初回の`scheduled_for`とする。

## 結果

存在しない月日、うるう年、存在しない第N曜日のいずれでも、YDR-013の前倒し・遅延・バックデート規則と`(task_rule_id, scheduled_for)`一意制約(YDR-012)を壊さずに次回Occurrenceを計算できる。#50の定例日基準Todoは、この規則をそのままロジックと自動テストに反映すればよい。

## 見直す条件

- 家庭ごとのタイムゾーン変更UIを追加する場合。
- 祝日・営業日・任意cron式など、暦規則自体を拡張する場合。
