# YDR-049: 会話操作を認証された共通ユースケースへ集約する

- 状態: Accepted
- 決定日: 2026-10-17
- 関連: [#189](https://github.com/upu/YAMORU/issues/189)、[v0.21.0](https://github.com/upu/YAMORU/milestone/21)
- 置き換える範囲: [YDR-008](ydr-008-ai-not-source-of-truth.md)のAIの用途を候補抽出・検索等の補助へ限定する部分。AIを正しさの基盤にしない原則と、人が解釈結果を確認できる要件は引き継ぐ。

## 背景

会話で「昨日フィルターを交換した」と記録し、結果と次回予定を確認したい。単に既存の画面actionを外部へ公開すると、ブラウザーの認証・再検証処理へ依存し、再送や同時更新の扱いが操作ごとに異なる。

利用者は#189の計画で、明確で許可済みの指示に不要な再確認を重ねず、曖昧な対象や必須値だけを質問する方針を選んだ。これはAIへ自由な判断権を渡すことではなく、利用者の指示を検証可能な操作へ変換する入口の追加である。

## 決定

1. Webと外部クライアントは同じユースケース層を使う。MCPは認証済みの構造化要求を渡すアダプタとし、周期・期限・在庫・権限を独自計算しない。外部からD1を直接操作させない。
2. 外部接続は利用者本人へ結び付け、家庭所属を毎回確認する。読み取り・家庭データ変更・個人通知設定・イベント購読を別scopeにする。家庭メンバーの役割は増やさず、既存の「家庭内は全員編集可能」と、外部へ委任する権限を区別する。
3. 認証はOAuthのauthorization code + PKCEを使う。既存Auth.jsはYAMORUへログインする入口として維持し、CookieやD1資格情報を外部へ渡さない。利用者が接続先と権限を確認し、後から解除できる。
4. 変更はprepare/commitの二段階とする。prepareは対象、実施日、変更範囲、差分、次回予定への影響を固定する。明確な指示と委任範囲に収まるときは同じ会話ターン内でcommitできる。候補が複数、必須値が不足、意味が変わる既定値、古いpreview、危険な取消は説明と必要な確認を行う。クライアントからの単なる`confirmed: true`を認可根拠にしない。
5. 操作ID・正規化payloadのfingerprint・対象revision・保存結果を共通契約にする。同じ操作の再送は保存結果を返す。同IDで別内容、他家庭・他主体での使い回しは拒否する。対象は特定のOccurrenceに固定し、再送や古い通知で次回分を完了させない。
6. actorは認証された本人、clientは接続元、performerは実施者として分離する。訂正は追記、取消は後続更新を壊さない条件でのみ許す。[YDR-015](ydr-015-occurrence-state-activitylog-history-safe-undo.md)、[YDR-026](ydr-026-completion-correction-events.md)を維持する。
7. 在庫の観測と補充は別の事実とする。「まだ残っている」から十分な量を推定せず、数量を創作しない。観測で補充日を更新しない。
8. 結果は対象・実施日・次回予定・訂正/取消の可否・詳細リンクを返し、利用者が確認できる。失敗、不確定、他の家族による完了を成功と混同しない。家庭内のメモや名称を操作命令として扱わない。

詳細な入出力・状態遷移・実装担当は[会話連携設計](../product/conversation-integration.md)を正本とする。公開する契約に対して後続Issueで実装し、この決定だけで接続済みとは扱わない。

## 比較した案

- 既存画面actionを直接MCP化: ブラウザー依存と操作ごとの再送差が残るため採用しない。
- AIに家庭全件を渡して状態と周期を計算: YAMORUとの二重の正本になるため採用しない。
- 全変更で追加の確認を要求: 明確な指示も二度説明する負担があるため採用しない。サーバー検証と、必要な場合の確認に分ける。
- 共通契約と薄いアダプタ: 今回採用。dot以外にも同じ境界を利用できる。

## 結果と見直す条件

Web更新も含めたrevision管理、全操作の冪等性、接続解除の検証が必要になる。#435〜#439で段階的に導入し、適用済みmigrationと既存履歴を保持する。利用者が許可した内容を説明できない、実装上のrevisionが既存Web更新を捕捉できない、接続先で認証契約を満たせない場合は公開を止め、設計を見直す。
